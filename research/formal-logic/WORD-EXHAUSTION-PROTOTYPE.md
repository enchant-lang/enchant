# A small proof strategy for finite word questions

The isolated module in `prototypes/word-exhaustion` passed **82 assertions** on
the selected immutable word SDK. The [qualification](evidence/word-exhaustion-prototype/qualification.json)
binds the exact source, actual native comparison and resource-capped run. It is
outside the SDK, the common answer certificate slot and compiler decisions.
The live word chapter retains its separately dated SDK qualification scope.

A native unsatisfiable answer remains a claim. A separate exhaustive checker
can establish some small finite propositions by deriving every possible Boolean
and word valuation itself and independently replaying the complete question.
Its candidate object carries the complete original subject reference, the named
word semantics and one fixed strategy. A proof can be checked again for another
backend without rewriting its mathematical statement. Each returned checking
record separately binds its actual full request reference.
It accepts no supplied valuation list, sampled coverage, native status, cached
forest or checked flag. Creating a candidate establishes nothing.

The prototype admits at most five combined variable bits, 32 valuations, 64
typed nodes and 16-bit intermediate word sorts. It checks the domain bound
before constructing its power. All terms must have Boolean or word sorts;
quantifiers, bound variables, functions and other operator families are refused.
Each point uses fixed SDK resource caps, including 100,000 point work units
and 128 visited nodes. The product of the point and work ceilings is bounded
by policy; this is no allocation or CPU theorem. An external runner still needs
its own whole-process deadline and memory cap.

The checker reconstructs the original request, freshly admits its actual graph,
derives the variable domains and uses the SDK's private point operation. Each
case needs valid coordinate bindings and an actually false assertion in the
assumptions plus the negated claim. An invalid coordinate cannot discharge a
case. An incomplete demanded evaluation establishes no result for that case.
A case satisfying all assertions returns its actual counterexample.

Complete coverage yields conditional entailment for proof questions or
unsatisfiability for SAT questions. Inconsistent assumptions can yield that
conditional result; their feasibility is deliberately not established. The
question's complete graph and named word semantics determine the logical
statement. The full request reference separately binds checking policy and
backend settings. The fixed checking strategy uses its own conservative resource
ceilings, without changing the mathematical word operators or adding assumptions
to the subject. It is an independent checking operation, rather than execution
of the native request. Before entering the common answer interface, its own
checking work must be composed with that interface's caller resource account;
this prototype does not establish that integration contract.

The actual checks cover every valuation at widths one through five,
wrapping, actual false claims, mixed Boolean/word domains, contradictory
assumptions, changed logical-subject references, reuse across backend choices, added trust/coverage
fields, floating versions, oversized domains, unbounded sorts, unused quantification and solver-denied
execution. A separate [recorded comparison](evidence/word-exhaustion-prototype/native.json) asks both real native owners for the
same three-bit wrapping theorem: native UNSAT must remain a solver claim, while
the independently exhausted candidate checks all eight points. Both actual
native owners returned UNSAT, retaining the solver-claim verdict. Their exact
identities, question references and independent checking records are saved.

This implementation run still trusts this enumeration checker, SDK
admission and word semantics, BL compilation and BEAM. It would establish no
mechanical soundness theorem, Source outcome relation, checked native history,
compiler preservation, general QF_BV completeness or language-wide totality.
The next architectural step would connect a reviewed proof strategy to the
common answer interface while retaining these separate assumptions.

The checked result also reconstructs an assumption ledger from the
actual admitted question. Each label points to its original term node under
the bound complete-subject reference, rather than exporting owner-local term
IDs as portable meaning. The negated goal is not listed as an assumption.
Feasibility stays unestablished. A changed premise changes the logical subject
and refuses the old candidate; changing only the requested backend preserves
the statement but changes the separately reported execution request reference.

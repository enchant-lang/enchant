# One question, several independently checked kinds of evidence

The source in `prototypes/evidence-bundle` is a pending isolated prototype. It
has not passed its functional gate and changes no SDK or default effect handler.

An engine report, a checked point and a checked certificate answer different
questions. Preserve those results independently. A native UNSAT label must not
become a proof; an invalid supplied point need not invalidate a separately checked
conditional theorem. If two independent checks really disagree, expose the
conflict rather than choosing a preferred backend or pretending agreement.

`propose` takes the existing original request and an ordinary map containing
`:answer`, `:certificate`, or both. The original fresh/retained answer versions
and their provenance remain intact. A new evidence bundle references that
complete request and subject and stores each candidate as a public data graph.
No supplied checking result, quota receipt, trusted flag or callable is accepted.
This adds a checking composition layer, not another term language or solver owner.

`recheck` validates each axis freshly. The existing answer reader handles native
claims, context composition and points. The only installed certificate strategy
in this prototype is finite word exhaustion. It cannot dispatch to a function
named by data. The result exposes `:answer-check`, `:proof-check`, `:proof-account`
and `:conclusion`, with execution/compiler/storage authority still false.
Conditional entailment retains the checker trust list and exact assumption ledger;
feasibility does not appear merely because entailment was checked.

The caller supplies a separate proof-checking allowance. Before invoking the
checker, reserve its complete fixed bound: 100,000 admission units plus 32 points
at 100,000 units each, totaling 3,300,000. Small questions deliberately reserve
that same maximum in this first interface. The allowance is a named convention,
not CPU time, memory usage or a proved physical cost model. The existing point
account remains separate and visible. Better demand-sensitive proof reservation
needs a reviewed integration with the canonical admission/point scopes.

Checking-policy and evidence references bind the actual checking invocation.
They do not change the certificate's backend-independent mathematical statement.
Changing a backend requires rebinding the outer bundle; the same proof candidate
can still be checked against that new request. A saved packet contains only the
original request and candidate evidence. Reopening uses the reader's current
allowance and runs the checks again. A producer's saved success is not an input.

The prepared gate tests closed envelopes, changed subjects/adapters, false proof
flags, exact allowance boundaries and refusal before checker invocation. It also
captures both actual native UNSAT reports beside independent eight-point results,
then reopens both packets in a fresh SDK-only process with only the two prototype
imports. That reader denies oracle calls, counts actual native exchanges, checks
warmed atom stability and exercises six tamper/budget controls.

This is preparation toward a common checking seam. Default oracle integration,
durable ledger indexing, generalized certificates and Source/compiler outcomes
remain separate implementation work. The isolated checker itself is not
mechanically proved sound. A successful gate cannot establish language totality.

# Staged language request integration

This is an implementation workspace inside the integration checkout, outside
the running managed-owner corpus's source/import path. It contains proposed
language code; none of it is selected by the live project or qualified yet.
It reuses the one immutable managed-owner SDK candidate and creates no SDK.

`formal.request-preview` separates the original subject, normalized numeric
policy and requested backend/deadlines. Its reference binds a freshly checked
complete subject reference, without expanding original term arguments or
encoding the entire graph as another graph merely to identify the request.

`formal.request-point-preview` provides fresh pure replay for effects and
durable readers. It checks bindings and actual assertions before observation
roots. Invalid supplied points, incomplete replay and admission refusal remain
distinct. Full structured observation materialization stays deferred.

`formal.request-answer-preview` binds a closed raw-evidence envelope. A caller
cannot submit a verdict, validation or proof bit. Fresh rechecking derives
point outcomes; native UNSAT remains a solver claim. Its current native bridge
requires a fresh owner. Retained-session request execution needs an owner-side
adapter/context extension before it can be exposed.

`formal.request-run-preview` uses the existing `:oracle` effect's explicit
`:request` method. Handlers can supply coordinates or delegate to a leased,
same-process, single-use fallback. Local matching provenance is separate from
portable evidence. The owner operation and the independent pure recheck have
separate scopes/accounts; `owner-ms` does not bound arbitrary handler code.

`formal.request-ledger-preview` reuses the existing ledger's payload and witness
presence transport, under a distinct recorded-request modality. Reopening
fetches and verifies that payload before fresh point rechecking. First-class
request indexes and split graph bodies remain SDK ledger integration work.

The test file covers complete identity, large ignored history without decoder
or normalizer calls, false/missing/ill-sorted points, actual counterexamples,
effect denial and lifetime, both native owners, changed fallback coordinates,
ledger transport and assurance tampering. The focused file passed 120 assertions on the exact candidate-3 SDK, including
both native backends. This is a limited implementation checkpoint: the separate
fresh-reader/key probe exposed the SDK application-key materialization gap, so
this code is still staged and unpromoted.

supervision after active managed-owner checks finish. That driver refuses overlap.

in `evidence/request-interface/supervision-retirement.json`. It uses the existing exact candidate SDK,
one cold VM and private capped directories, and records committed source pins.
Further fresh-process persisted-ledger checks and integration remain required.
Promote reviewed code into the normal project/SDK interface in a coherent batch;

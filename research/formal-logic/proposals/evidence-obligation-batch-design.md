# Next coherent runtime batch: logical evidence and obligation acceptance

The scalar SDK is already qualified. The finite feasibility (35 assertions),
policy composition (93) and graph integer kernel (54) are separately qualified
prototypes. This document designs their integration; it does not claim that the
selected SDK already implements it. Keep the current dossier inputs frozen.

## Keep the three judgments visible

A checked conditional theorem, feasible premises and an accepted request are
separate results. The next common answer should expose `:proof-check`,
`:feasibility-check`, `:logical-conclusion` and a policy-aware `:conclusion`.
Reusing `:conclusion :status :checked` for an obligation rejected by its original
`:vacuity :reject` would defeat the semantic fix. Preserve the mathematical
component while reporting the stronger request judgment explicitly.

Use the nine actual policy/feasibility cases already exercised by
`formal.finite-obligation`. `:allow` may accept a checked conditional theorem
with unestablished or inconsistent premises. `:report` exposes those cases as
conditional/vacuous reports. `:reject` requires a checked feasible background;
inconsistency rejects the obligation and unestablished feasibility leaves it
incomplete. A failed proof or conflicting independently checked results cannot
be accepted through any policy.

## One policy parser across all readers

Install the qualified ordinary-value/raw-row parser once. Update query creation,
query validation, the materialized graph reader and the graph-native inventory
reader together. Missing policy retains the historical default `:report`;
explicit nil, strings, booleans and unknown keywords refuse. Preserve exact
`:allow`, `:report`, `:reject` values, without interning arbitrary graph bytes.

Legacy native-only reports still describe an engine claim. Recognizing the new
vocabulary alone does not make those old compiler/oracle consumers independently
checked; migrate their acceptance rules deliberately after the common evidence
judgment is available.

## A closed proof strategy dispatcher

Data may select only installed certificate profiles, never a callable or module.
Initially install the finite Boolean/word strategy and the linear graph integer
strategy. The latter does not yet implement all piecewise/ground legacy rules;
retain that limitation. Both bind the complete original logical subject, excluding
backend/deadline choices from the mathematical statement while retaining the
complete execution request reference in the outer carrier.

Reserve the complete selected strategy before invocation. A simple initial
account reserves 3,300,000 units for finite checking or the fixed 2,000,000-unit
integer strategy. Caller allowances cannot enlarge domain bits, coefficient
size, node/depth or context limits. Incomplete resource checking is not a false
proposition. Keep primitive/point accounts separate from this aggregate policy
account and from physical process caps.

## General background derivation, separate feasibility evidence

Factor the finite prototype's original-graph SAT derivation into a common
assumption module. Freshly admit the original under a named checking policy,
patch only mode/claim/counterexample, and verify assertion-byte preservation.
Preserve observations, scope, origin and every retained assumption. The result
binds original and background subject references and the assertion graph.

For finite Boolean/word backgrounds, reuse the qualified finite search plus
independent witness replay. Reserve its complete 3,600,000-unit strategy before
invocation. Do not advertise this enumeration for unbounded integer or String
domains.

For integer backgrounds, support an explicitly supplied background point and/or
a candidate original-graph contradiction certificate. The point is checked on
the freshly derived background; the contradiction is checked by the installed
integer kernel. Neither a native UNSAT report nor the main conditional proof
establishes feasibility. Deriving a background may omit variables used only in
the claim; retain the derivation's scope and do not call its coordinate map an
execution of the original function.

If feasibility evidence conflicts, retain both components and refuse a useful
obligation judgment. Contract `requires` conditions already enter assertion rows;
do not guess contract preconditions by scanning implication antecedents.

## Carriers, records and fresh checking

Use a new closed carrier version/profile for new feasibility slots. Read old
answer/certificate carriers explicitly; do not silently accept extra fields in
the old shape. An outer carrier still binds the full original request. A
background point/certificate additionally binds the deterministic derived
background. Saved packets contain candidates, not producer checking results.
Reopening uses the current caller's proof and feasibility allowances.

A richer checking result needs a new named checking profile. Old packet bytes
and producer identities remain unchanged even when a new checker establishes
an additional feasibility fact. Qualification should compare the preserved
logical statement and fresh checks, rather than pretending the new result has
the old checking semantics. Add a durable bundle ledger only after its own
closed schema, payload/index binding, vocabulary and two fresh readers pass.

## Integration order

Batch parser, common background derivation, installed strategies, budget
composition and carrier/result changes before one new SDK. Reuse that immutable
artifact for policy controls, malformed candidates, real native/effect ownership,
old packet readers and Source/contract consumers. Keep the existing raw native
claim vocabulary visible until its consumers migrate. Refresh the dossier only
through actual source-backed producers, the real writer/check loop and inspected
browser frames. Compiler preservation and whole-language totality remain their
own implementation and theorem obligations.

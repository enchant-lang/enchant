* The big idea
#+begin_lede
Imagine writing a function and asking, in the same language: /what must be true before this runs, what can it return, and can this change break anything?/

The experiment gives Beam Lisp a common language of typed terms. Z3 and OxiZ can work on the same question. BL owns the meaning, and the answer brings its assumptions and limits with it.
#+end_lede

#+end_stats

#+begin_principles
Write the meaning once | Maps, arithmetic and outcomes keep the same meaning when we change the solver.
Make answers inspectable | Show the claim, its assumptions, a counterexample when available, and the scope of the result.
Use preview to improve the language | Fix incoherent behavior before programs have to depend on it.
Keep a clear next step | A language with precise semantics and checked proofs is a realistic direction. Every stage needs its own evidence.
#+end_principles

** The implementation is moving
The autonomous goal now works directly on main. The first slice is executable: =formal/certify= searches for a proof object, and =formal/check-certificate= checks it afresh against the exact claim, assumptions, profile and scope. Both operations use BL terms and need no native solver.

The checker covers Boolean case splits and contradictions made from linear integer inequalities. It also checks strict integer bounds and exact rounding when dividing coefficients. Search is deliberately incomplete: a missing proof returns unknown. Other theories are refused by this proof system even when Z3 or OxiZ can decide them.

The first focused run passed 577 assertions: 511 for certificate checking, 42 for the existing term boundary and 24 for the public API. This includes rejecting altered statements, missing branches, forged terms and invalid arithmetic weights. These checks test the implementation; they are not a machine-checked proof of its soundness.

#+begin_note :title "What a checked result means here"
The claim follows from its listed assumptions in the supported term logic, according to this checker. Assumption feasibility, the connection to source semantics, the checker implementation and its BL/BEAM execution still need their own assurance. A checked term proof does not silently grant compiler authority.
#+end_note

** Ordinary loops, with an unbounded argument
The next implementation accepts an ordinary BL =loop/recur= expression through the real compiler's ANF. A contract supplies a precondition, invariant, integer ranking vector and result condition. The tool checks initialization, normal evaluation on each reachable path, invariant preservation, strict rank decrease and the exit result. One decreasing counter handles a countdown; a lexicographic pair handles an inner counter that resets when an outer counter decreases.

These are symbolic arguments with no iteration bound. The separate reference executor has resource ceilings and reports incomplete work when it reaches one. A bad invariant or rank yields =obligation-refuted=: its countermodel may be unreachable in the actual execution. That does not establish nontermination of the program.

The focused loop/core/contract/API run passed 3,404 assertions, including 102 loop assertions. Six examples ran on both native backends with the expected results: three checked model arguments, a growing-loop rank failure, a loose invariant with an unreachable countermodel, and inconsistent inputs. An unused failing branch can carry an explicit inconsistency certificate. An author's =decreasing= assertion cannot replace a checked argument.

The loop checkpoint has twenty-two checked theorems. In addition to ranking orders, it defines an unbounded evaluator from a total controller and a well-founded back-edge relation, and proves that exit postconditions carry through that evaluation. Twenty theorem audits have empty axiom dependency lists. The two nonnegative integer ranking proofs use Lean's standard =propext=, =Classical.choice= and =Quot.sound= assumptions, which are listed in the receipt and returned rule metadata. The correspondence between the BL implementation and that mathematical model remains reviewed and unproved.

** Let the optimizer propose; make the evidence decide
The next piece compares two exact core programs. It asks whether they return the same value or raise the same named error under the same precondition. A separate optimizer now proposes real rewrites, and the translation boundary reconstructs the comparison from both programs. Only an independently checked proof lets that gate return the changed core. Other answers keep the original.

This catches a subtle mistake: multiplying an expression by zero still evaluates that expression. If it raises, replacing the whole computation with zero changes the program. Our rewrite keeps that evaluation before returning zero. Equal conditional branches likewise keep evaluation of the condition.

#+begin_sequence :title "A proposed change earns its evidence"
lanes optimizer · untrusted candidate | subject · exact core models | checker · portable proof | caller · explicit precondition
optimizer -> subject : Supply the original and changed programs.
subject -> checker : Rebuild the value, return and named-error relation.
checker --> subject : Check every case and arithmetic contradiction.
subject => caller : Return the changed core only with a checked comparison.
note subject, caller : An unknown, unsupported, vacuous or solver-only answer keeps the original.
#+end_sequence

The proof rules now handle conditionals inside linear integer arithmetic and ground division by a nonzero integer. Known logical guards let the checker ignore a value that cannot be observed after a failure. General nonlinear arithmetic and variable division still need broader evidence; an unproved rewrite stays behind the gate.

Native counterexamples also run through both concrete core programs. When OxiZ leaves an unused input opaque, BL can choose an explicitly labelled completion and recheck the whole counterexample. The chosen value never becomes a claimed native observation.

** A state promise, across every permitted step
A protocol model now describes named state fields, admitted initial states, message or transition variants, input assumptions, guards and updates. Its checker rebuilds the induction obligations from the closed definition. A proof must cover initialization and every transition. No cached success flag or missing transition proof can replace that coverage.

For an account, we can check that the balance stays nonnegative and that credits minus debits equal the balance. The argument covers every finite prefix of permitted model steps, with no trace-depth limit. Input assumptions say which messages the model admits. Initial feasibility is shown separately by a replayed state or native witness.

#+begin_rosetta
What the model observes | What happens to the state | What the evidence records
A false guard | The transition is disabled. | It cannot occur as an executed trace event.
A failed guard or update | The old state is retained. | The failed attempt stays visible to safety.
A successful update | All fields read the same old state, then commit together. | The next state and invariant are replayed.
An input outside the assumptions | The event is outside the declared environment. | The trace is rejected with that reason.
#+end_rosetta

A failed induction obligation can describe an invariant state that no execution reaches. We call that =obligation-refuted=. A concrete replay is separate evidence: it checks an admitted starting state and an explicit sequence of model events. Failure and stuttering remain visible in that sequence.

The focused run passed 648 assertions, including 133 new protocol assertions and the existing feature, advanced, API and common-interface checks. The state-induction checkpoint has 25 checked theorems. Its three new induction and failure-exclusion theorem audits are empty; the two integer ranking proofs retain their listed standard assumptions. The BL implementation-to-model connection remains reviewed and unproved.

** A solver answer you can run, step by step
Bounded safety is now a closed subject too. The question carries its exact state model and depth. A proof for depth one cannot stand in for depth two. The decoder reads native choices and inputs, runs the declared model independently, and checks the resulting states against every unrolled assertion and concrete native observation.

Consider a counter starting at zero, increasing by one, with the promise that it stays below two. A depth-one search finds no violation. At depth two, both backends produce a trace through zero, one and two. That answer now includes the actual events and replayed states, rather than only a satisfiable formula.

#+begin_rosetta
What comes back | What BL checks | What we may conclude
An unsafe native model | Initial admission, choices, inputs, every state and the negated safety claim | A valid replay establishes an unsafe trace of this declared model.
An opaque unused scalar | An explicitly labelled completion, followed by the whole replay | The chosen value belongs to replay; it is not a new native observation.
A failed attempt | Old state retained, failure recorded, only stuttering afterwards | Later steps cannot erase that failure.
A repaired final state | Every earlier prefix as well as the final state | An earlier invariant violation still counts.
A safe bounded answer | Its exact bound and any independently checked certificate | It covers that bound; an unbounded argument is a separate subject.
#+end_rosetta

** A promise about the function you actually wrote
The next connection is now implemented: ordinary record-shaped source functions can carry contracts, and state transitions can be derived from actual handler source. You write a function that reads a state and a message and returns the next state. The interface extracts its real compiler ANF; it does not ask you to rewrite that update as a second model callback.

Records keep one whole-expression outcome. Reading a useful field cannot hide an error in another field. Updates evaluate their arguments in order, and an eager lookup default can still fail when the key is present. These details make the source promise meaningful.

#+begin_sequence :title "The handler earns a source connection"
lanes source · ordinary BL | core · closed records | model · state promises | checker · evidence | run · concrete trace

core -> model : Derive every state field and the whole-handler outcome.
model -> checker : Rebuild the source connection and check all induction premises.
checker --> model : Return a source-bound proof object.
model -> run : Replay the model and execute the handler core for each step.
note source, run : Live actor behavior needs its own observation and refinement contract.
#+end_sequence

Even the right function name can resolve to a different implementation. The next probe replaced only =assoc= in an owned child environment. The formal state update stayed the same, but the ordinary compiled handler returned a replacement state. The observer caught that disagreement too.

Lean now applies that argument to the exact finite initializer and controller. A finite return trace exists for every admitted input, and the result meets the postcondition at its exit state. The theorem uses no fixed iteration bound.

Two ranks | The outer rank can decrease while the inner rank resets upward.

* Could Beam Lisp be fully formal?
Yes, if we choose a precise promise and build toward it in layers. There are several different ambitions hiding in that phrase.

Fully formal and total are different ideas. A formal semantics can describe divergence, exceptions, nondeterminism and long-running processes. A total core is an optional foundation choice for computations and proof terms that must terminate.

#+begin_rosetta
Ambition | What it would mean for BL | What it does not buy automatically
Precise semantics | Every core construct has a mathematical account of values, outcomes and effects. | A proof that every program meets its author's intent.
Proof-aware programs | A module can carry contracts, assumptions and checked evidence. | A decision procedure for every possible property.
A total core | Core functions terminate; recursion needs a structural argument or another checked termination proof. | A ban on long-running actors in the effectful language around it.
A verified compiler | Compilation preserves the specified source behavior under an explicit target/runtime model. | Verification of OTP, the OS, hardware and every foreign library.
A fully verified application | Its stated end-to-end properties follow from checked component proofs and explicit environment assumptions. | Proof that its requirements are complete or the real world obeys those assumptions.
#+end_rosetta

** The direction I would choose
A small pure core, a rich effectful language around it, and evidence that travels with the code. Keep ordinary programming pleasant. Make a stronger claim require a stronger, visible justification.

#+begin_principles
Specify the core | Values, equality, evaluation order, exceptions and the meaning of each numeric/text operation belong in a precise semantics.
Distinguish partial correctness and termination | “If this returns, its balance is nonnegative” differs from “this always returns.” Total correctness needs both.
Keep effects explicit | Host calls, state, actors, time and failures need contracts and trace semantics. A snapshot becomes a stated assumption.
Make proof search replaceable | Solvers and tactics can propose evidence. A small checker validates supported proof objects against the exact claim.
Carry the dependency ledger | Report the definitions, assumptions, axioms, profiles, artifacts and runtime contracts each theorem uses.
Preserve meaning through compilation | Prove a lowering pass or validate each translation; retain the source-to-ANF-to-target connection.
#+end_principles

** Can it still feel like a Lisp?
Yes. The surface language can keep macros, interactive evaluation and convenient data structures. The formal boundary would sit underneath, after names and macros have been resolved into a small core.

A macro can generate code and proof obligations without becoming trusted. A tactic can search for an argument without becoming trusted. The checker judges the resulting core term or proof object. Arbitrary runtime eval and unmodeled host calls still need an explicit boundary.

Dynamic values can enter a checked module through a predicate or checked conversion. A theorem may then say “for every input admitted by this contract.” It should not silently turn Any into a precisely typed value. A staged or gradual adoption path could keep ordinary BL useful while selected modules make stronger promises.

A recursive definition in the total core | Its recursive calls decrease in a checked well-founded order.
A long-running actor | Its transition function and permitted traces satisfy the declared safety rules; progress has separate assumptions.
A macro or proof tactic | Its generated output passes the same checks as handwritten output.
A host call | Its trusted contract or runtime check is visible in the dependency ledger.
#+end_rosetta

** What should count as a proof?
The first practical target could be a narrow certificate system for a useful fragment. Equality and linear integer reasoning are possible starting points; exact proof rules, integer cuts and normalization would need careful specification. A general SMT proof can contain theory lemmas, so checking only a propositional SAT certificate would leave part of the argument unchecked.

There are several viable foundation choices: a logical framework with explicit inference rules, a dependent type theory, or an external proof assistant that checks exported statements. We should choose one small trusted route before committing to a large proof language. The present portable term layer can feed any of these; it does not force BL to copy Lean's surface syntax.

A checked proof should name the exact claim, semantic profile, definitions and assumptions. Its validity should follow from those meanings and proof rules. The solver build that discovered it remains useful provenance; it need not become a logical premise once an independent checker validates the full proof.

#+begin_decision :id formal-kernel-strategy :title "Start with a small checked fragment, then grow" :status proposed
- [x] Pick one proof system and one useful fragment, with an explicit assumption ledger and independently checked proof objects.
- [ ] Build a large new proof assistant before testing a useful end-to-end contract.
- [ ] Label every solver UNSAT result as a checked theorem.

A possible first slice is an integer contract through resolved ANF, with a checkable argument for a narrow class of obligations. It must demonstrate both the proof rules and the source-to-statement connection.
#+end_decision

** The compiler and the checker also need a trust story
Self-hosting a checker in BL does not verify the BL compiler. If the compiler or runtime misexecutes that checker, the logical boundary can fail. We should record that dependency, use an independently implemented checker, or verify/validate the relevant compilation path. Bootstrapping and packaging are part of the architecture.

For the compiler, two routes can complement each other. We can prove selected lowering or optimization passes once, or validate individual translations against their input. Both need the intended observation relation: successful values, exceptions, effects and traces. Equality of two values alone may be too weak to justify substituting one representation for another in every program context.

#+begin_honest :title "A proof still depends on a statement people can understand"
The strongest result is useful only when the contract describes the behavior we intended. Keep the exact statement, examples, counterexamples, assumptions and trust dependencies readable beside the code. Formal foundations should make those conversations easier.
#+end_honest

** The important limits
General recursion makes automatic termination and arbitrary program correctness undecidable in general. We can choose decidable fragments, accept user-supplied invariants and termination arguments, or return unknown. “Formal” does not mean the machine can answer every question. See [[https://www.cs.virginia.edu/~robins/Turing_Paper_1936.pdf][Turing's original computability result]] and [[https://lean-lang.org/doc/reference/latest/Definitions/Recursive-Definitions/][Lean's explicit treatment of recursion and termination]].

Actors can run indefinitely by design. We can prove safety (“no invalid message is sent”) while leaving progress conditional on scheduler fairness, delivery and failure assumptions. Cancellation, timeouts and hot upgrades need their own observable trace semantics.

Foreign calls should expose explicit contracts and admission policies. Treating an unmodeled host function as a pure mathematical function would hide exactly the uncertainty the interface is meant to reveal.

A checked proof can still establish the wrong specification. We need understandable contracts, executable examples and witnesses to help people review whether the claim is the one they intended. A typed witness now lets us show that a set of preconditions actually has an example, alongside the separate proof of what follows from those preconditions.

The [[#prove-the-promise-on-the-core-program][checked Core contract]] makes one part of that design concrete. For every admitted input, a must-return program in the finite Core fragment yields a value that meets its contract. Named failures can be tracked explicitly by a different policy. This gives us a place to attach a checked decrease argument when the fragment grows to include loops.

#+begin_honest :title "A total core inside an effectful language"
I recommend exploring a total, pure core with explicit effects around it. Keep a supported general-programming path for actors and interop, with its assumptions visible. That gives BL a strong foundation without pretending the entire BEAM and outside world are already verified.
#+end_honest

** What this could feel like
#+begin_quote
“This refactor preserves the result, the failure behavior and the declared effects. Here are the assumptions it uses. This module still relies on an unverified host contract.”
#+end_quote

That is a useful language feature: a concrete, inspectable statement attached to the program. A proposed declaration might combine a precondition, a result contract, an effect signature and a termination claim. The exact surface syntax should follow the semantics, rather than deciding the semantics accidentally.

** What native means for Beam Lisp
The common interface gives Beam Lisp ownership of its symbolic vocabulary, language outcomes, sharing, source maps and evidence. Both native workers can consume that vocabulary: Z3 has native C AST constructors and OxiZ has Rust term APIs. Both still need an adapter from BL data and an owned native lifetime. Native ASTs remain private to the worker while the immutable BL question can travel, be inspected, cached and replayed.

This architecture makes finite maps, tagged outcomes, coverage, permission relations, induction and synthesis reusable language features above either engine. Backend differences remain concrete questions about supported constructors, solver strength, observations, cores and retained artifact behavior. An OxiZ source module or a Z3 theory name alone establishes none of those results; the two corpora below provide the comparison at explicit scopes. Performance and memory advantages require their own measured workload evidence.

** What the exact runtime taught us
#+begin_honest :title "A concrete equality defect, with a small proposed fix"
The pinned SDK returns [true true false] for [(= 1.5M 1.5) (= 1.5 1.50M) (= 1.5M 1.50M)]. This violates transitivity. The cause is the scale-sensitive two-Decimal exception inside an otherwise exact-rational numeric family. The proposed fix removes that exception and exposes representation or quantization equality explicitly. Production runtime source has not been changed by this experiment.

Cross-list/vector value equality is a separate design choice: it can remain useful even when conj and type-sensitive operations distinguish the representations. Compiler rewrites must use a relation that respects the observable context.
#+end_honest

The common facade is formal.api: symbols declares a caller-prefixed schema, question builds a portable obligation from typed values, describe exposes its terms and scope, and check chooses the backend. Pure BL callbacks build the model; executing a callback is not a proof about arbitrary callback implementation code. construction-capabilities exposes the native advertisement, while the retained corpora establish tested capabilities.

This static example documents the implemented low-level interface; it is not an executed document cell or a handwritten solver receipt.

(ns example.formal
 (:require [formal.term :as t] [formal.query :as q] [formal.logic :as logic]))
(let [x (t/variable "x" t/Int)
      question (q/prove (t/ge (t/add x (t/int 1)) (t/int 1))
                 {:id :increment
                  :profile :math/unbounded-int-v1
                  :assumptions [(t/ge x (t/int 0))]

  (logic/run {:backend :oxiz} question)])

The shared layer also implements scalar projection enumeration, bounded integer optimization, finite-grammar synthesis and derived deletion explanations. Passing api/backend assertions cover concrete scenarios; those algorithms do not become native Optimize, MaxSMT, unrestricted synthesis or certificate-producing proof systems.

Advanced value prototypes add bit-field layouts, explicit byte order, pack/unpack lenses and wrapping/checked words. Their floating outcomes use declared binary16 with RNE; all 31 expected advanced results matched on Z3, while OxiZ retained twelve unknowns and two unsupported results. This does not qualify BEAM binary64 source arithmetic. Arithmetic replay limits remain explicit even when the native solver proves an obligation.

A total SMT Array has no finite extent or absence; a finite BL Map needs presence and extent descriptors. A Seq is not an effectful lazy stream. Finite sets, bags, maps and tagged sums are explicit language encodings above primitive terms, so their qualification is separate from native Set/Bag/recursive-datatype APIs. SMT FP equality, IEEE fp-eq and raw bit identity are also different relations: SMT has one NaN value, payload retention needs raw bits, and source-native BEAM floats exclude NaN and infinity.

** Define the boundaries
#+begin_terms
term | immutable typed expression whose meaning is independent of a solver
language value | payload plus runtime-definedness, representation bounds, constraints and decoding domain
native AST | private backend object retained behind an owner and generation
theory | a semantic vocabulary and the laws it denotes
procedure | a verification or search method over terms, such as induction or repair
observation | a captured runtime fact whose freshness and authority remain outside SMT
qualified capability | retained evidence for an operation, sort, result kind, profile and bound
certificate | checkable evidence, separate from a solver verdict or model concreteness
#+end_terms

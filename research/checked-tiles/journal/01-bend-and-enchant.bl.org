#+subtitle: A design discussion grounded in source, execution models and measurements.

* Why compare these languages?
#+begin_lede
*Bend’s advantage is that one decision by the programmer does several jobs.* When you write a pure function over values with explicit ownership, split it into independent calls, and state a law about its result, the checker and the runtime can both use what you wrote. The checker gets a tractable recursive program to reason about. The runtime knows where it can transfer ownership, run branches concurrently, and join their results. The application author can point to the function, its law, and the call that runs it on the GPU.

*Enchant has much of the underlying machinery, and in several areas asks harder questions. Its weakness is the distance between those pieces for someone writing an application.* I found an Enchant function whose contract can be checked, a selected Source export whose actual execution can be observed, a byte pipeline that runs through four execution paths, a renderer that uses the GPU, and a native image that rebuilds itself. Each is substantive. The missing demonstration is an ordinary application definition that participates in all the relevant paths, survives a live edit, and gives its author a clear answer about what was proved and what actually ran.
#+end_lede

I compared Bend 2 at =9c586f09= with Enchant =main= at =08610e219=, including Enchant’s October Bend assessment and the November formal, native, and deployment work that changes its conclusions. The measurements below are the projects’ retained results. I inspected the sources and evidence without rerunning either benchmark suite.

* What Bend actually brings together

The original Bend and the current Bend use different execution models. *Bend 1 used HVM and interaction nets. Bend 2 uses neither.* Anyone starting from the famous Bend 1 demonstrations could spend months trying to reproduce machinery that the Bend team itself replaced. The current design is in some ways more interesting for Enchant because its core ideas can be adopted independently. [[https://github.com/HigherOrderCO/Bend1][Bend 1]] · [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/bend2/docs/BendRT/main.typ][Bend 2 runtime paper]]

*On the execution side, the programmer supplies information that would be expensive or impossible to infer reliably.* A parallel =let= says that several calls can run together and promises roughly balanced work. A =!= marks a call for GPU execution. Affinity constrains how live values can be used. Duplicable data, borrowed arguments, and values with one owner can receive different treatment. The compiler can turn a consuming match into reclamation, lend a read-only argument without reference-count traffic, and give a task ownership of its arguments. It lowers calls to jumps, explicit continuations, and joins inside a flat evaluator. CPU and GPU executors use the same generated computational segments. This is how a recursive tree program can execute on a GPU without a GPU call stack or a second handwritten implementation of the algorithm. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/bend2/docs/BendRT/main.typ][Runtime design and compilation]]

*The price of that simplicity is visible in the performance data.* The scheduler grows a frontier of tasks and then lets lanes drain their work. It has no work stealing. One expensive branch can determine when a whole wave finishes. The equal-work promise is unchecked. GPU dispatch also has a specific context in which it takes effect, and the runtime described in the paper runs CPU and GPU computation in turn. Apple unified memory makes the handoff particularly attractive. CUDA managed memory can still move pages across PCIe. Bend’s shader guide shows how much deliberate work went into a fast frame, down to tile size, fork depth, and flat inner loops. The programmer gets to write all of that in Bend. Hardware-aware algorithm design still matters. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/bend2/docs/BendRT/main.typ][GPU execution and limitations]] · [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/guide/SHADERS.md][Shader authoring guide]]

Here are four rows from Bend’s published September M4 Max runtime pin, in seconds. The C column is the project’s C baseline. The GPU measurements are Metal on this machine.

| Workload | Bend, one CPU thread | Bend, parallel CPU | Bend, GPU | C |
|----------+----------------------+--------------------+-----------+-------|
| Game of Life | 7.803 | 0.647 | *0.063* | 6.776 |
| Mandelbrot | 4.473 | 0.395 | *0.057* | 3.750 |
| Lexer | 2.144 | *0.198* | 1.075 | 1.036 |
| Hash map | 2.741 | *0.238* | 0.521 | 0.622 |

The impressive result is that the language delivers both the 63 ms Game of Life and the 198 ms parallel CPU lexer. A policy that sent both workloads to the GPU would make the lexer more than five times slower than its parallel CPU path. The hash-map row also illustrates how much ordinary representation costs can matter even in an affine native language. These are comparisons against particular implementations on particular hardware. The BendRT paper explicitly identifies CUDA as implemented and unmeasured in that paper. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/bench/runtime/_pin_/apple_m4_max.txt][Pinned runtime results]]

*On the proof side, developers write proofs in Bend.* A law is a type, and a proof is a definition inhabiting that type. Pattern matching and recursive calls give authors a direct way to prove a property by induction. =LAWS.bend= holds the human-owned specification and =PROOF.bend= imports and discharges it. Ordinary checking and =--verdict= do different amounts of work. The latter translates the checked definitions into BendTT and runs a second checker built from the Lean implementation. Its formalization includes soundness for the declarative theory, termination of live evaluation under its conditions, and consistency. The guide explicitly identifies the source-to-BendTT translation as unproved. The runtime paper separately identifies the C runtime as unverified. The Lean results apply to the kernel calculus. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/guide/GUIDE.md][Language guide]] · [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/bend2/bendtt.lean][Lean kernel and theorem statements]] · [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/bend2/safe.ts][Verdict implementation]]

Two examples explain the distinction better than the headline:

- *The parallel sum is the real synthesis.* Its law says that for every natural depth and starting index, the fork/join tree sums the same numbers as a sequential specification. The implementation’s recursive decomposition gives both the runtime its parallelism and the proof author an induction structure. That is a property worth proving even on a machine with no GPU. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/demos/pure_par_sum/LAWS.bend][Parallel sum law]]
- *The ray tracer shows the boundary.* Its laws prove that Esc quits regardless of subsequent events and that reading a key after setting it yields the value just written. The file explicitly excludes the F32 scene from its claims. A ray tracer can run on the GPU and have meaningful machine-checked laws while its pixel arithmetic remains outside those laws. Reading the law file tells a user exactly what they bought. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/demos/app_ray_tracer_3d/LAWS.bend][Ray tracer laws]]

* What this changes about my assessment of Enchant

** 1. Enchant already knows how to make code fast. It needs to make that knowledge available at the source level.

The strongest Enchant experiment here runs *the same compiled byte kernel* through a resident port, a bounded regular NIF, and a dirty CPU NIF, alongside generated BEAM. At 256 bytes, the wrapper-inclusive medians were *0.988 µs* through the regular NIF and *22.542 µs* through the port. At 1 MiB, the regular path refused the work by policy. The dirty NIF took *2.897 ms*, the port *6.879 ms*, and fused BEAM *64.745 ms*. The experiment also measured unrelated scheduler heartbeat under contention. That last measurement matters to anyone putting a kernel inside a live service. [[file:../../rt-selfhost/invm/RESULTS.md][Direct native entry results]]

Enchant also has a source-lowering spike for pixel loops. It identified a useful ownership fact without imposing affine types across the whole language. A loop that functionally constructs a *fresh* output one pixel at a time can lower to a native store into that output. The spike reported byte-for-byte agreement over a 1 MiB blend and a roughly 145× kernel improvement over its BL-on-BEAM baseline. Meanwhile, the more thoroughly measured fusion experiment admits one exact descriptor. Those are complementary achievements. One shows that a source idiom exposes enough structure. The other shows what happens to the gain once the application pays the real call boundary. [[file:../../lowerers_spike/INSIGHTS.md][Pixel lowerer findings]] · [[file:../../rt-selfhost/fusion/RESULTS.md][Fusion experiment and timing boundaries]]

My criticism is that *the next application author still has to rediscover the connection between those achievements*. The interprocedural eligibility implementation can identify candidates using effects, termination, and result sort. Its own source says argument representation and bounded work remain downstream obligations. The native-region plan already identifies extraction from ordinary source, numeric semantics, ownership, backend choice, and invalidation. Bend supplies a reason to prioritize finishing that path over commissioning another backend comparison. The bottleneck is now whether a *second independently written function* gets the benefit through the normal compiler. [[file:../../../priv/lib/native/eligible.bl][Eligibility implementation]] · [[file:../../../!tasks/plans/PLAN-140-make-pure-data-regions-a-bl-compiler-exe.org][Pure data region plan]]

** 2. The November work changes what “native” should mean in this discussion.

Enchant’s Gambit-based native image, its Cranelift kernels, and its graphics workers solve different problems. The self-hosting work achieved a byte-identical stage-two/stage-three Scheme fixed point, exercised the compiled actor matrix across three stages, and qualified cross-target JavaScript traces. Preparing boot macros reduced median first-result latency on the same native image from *695.14 ms to 161.77 ms*, across eight fresh processes per variant with warm filesystem caches. The compiler pipeline measurements also document cases where BEAM wins. The startup result directly benefited from eliminating repeated preparation. A faster arithmetic backend would have missed the dominant cost. [[file:../../native-seed/speed/native-speed.bl.org][Native Speedwork and final qualification]]

I would keep the native seed focused on self-hosting, deployment, and the workloads its profiles identify. I would judge packed compute by throughput, representation, and boundary costs. I would judge the live system by edit-to-accepted-result latency and continued service. A single “native speed” target makes it too easy to optimize the wrong one. Enchant even has a live Work activation through the native controller, with controller replacement under outstanding work tracked separately. That is a product capability with a very different acceptance test from Mandelbrot. [[file:../../field-station/PROJECT.bl.org][Live controller acceptance]]

** 3. Enchant’s proof gap is narrower, and more interesting, than “Bend has Lean.”

Enchant already has independently checked certificates, exact question identities, replayable witnesses, Lean models, and proofs about selected Core programs. Its Core contract work connects an entailment to the *returned value or permitted named error* of the contained program. Its protocol work establishes invariants over *every finite prefix* of a declared transition system. Its selected-runtime observer can initialize the original linked Source unit, invoke the selected export on a concrete input, and check its retirement. Each addresses a different way a plausible claim can be wrong. [[file:../../formal-logic/CORE-CONTRACTS.md][Core contracts]] · [[file:../../formal-logic/PROTOCOLS.md][Protocol induction]] · [[file:../../formal-logic/SELECTED-RUNTIME.md][Selected runtime observation]]

There is also an example where Enchant’s insistence on these distinctions paid for itself. A legacy verifier reported a complete proof over mathematical reals for a cancellation property that failed in compiled execution at =1.0= with =0.1=. The later work introduced a finite-binary64 Source profile and made known mismatched legacy claims refuse. Bend’s own limitations describe F32 as axiomatic. For numerical acceleration, Enchant has already uncovered exactly the kind of semantic error an optimizer could otherwise amplify across millions of elements. [[file:../../formal-logic/FLOAT-SOURCE.md][Enchant binary64 investigation]] · [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/README.md#limitations][Bend limitations]]

*Where Bend is ahead is the authoring experience for a general recursive law.* Its insertion-sort example says both that the result is ordered and that every value occurs the same number of times as in the input. A sort that always returns the empty list satisfies the first property. A human can read the two laws together and see why the second matters. Enchant’s protocol induction is powerful for state machines, while its selected scalar Source property route explicitly refuses recursion. I would use sorting or a recursive tree rewrite as a design test. Can an Enchant author state a theorem over arbitrary lists or trees, name a reusable lemma, and see the precise subgoal left by an edit? More supported solver theories alone will not supply that experience. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/demos/proof_insertion_sort/LAWS.bend][Bend sorting laws]] · [[file:../../formal-logic/SOURCE-PROPERTIES.md][Enchant Source property scope]]

** 4. Enchant’s strongest opportunity is attaching a law to a running revision.

Bend gives an agent an excellent collaboration protocol. A human owns the law. The agent edits the implementation and proof. A single command has a meaningful exit status. Enchant’s obligation interface has more of the hard parts than the October assessment suggests. It reconstructs the subject, checks required rows, keeps missing evidence visible, distinguishes an unreachable path from a proved claim, and tracks feasibility separately. The documentation also says that checking these data does not automatically grant compiler authority. [[https://github.com/bendlang/bend/blob/9c586f094f4fc88bef440dc8b4d77a2f92c257cc/guide/GUIDE.md][Bend law workflow]] · [[file:../../formal-logic/OBLIGATIONS.md][Enchant obligation interface]]

Enchant can turn that into an answer Bend’s command does not attempt to give. *Which revision is serving this request, which law admitted it, and what happens to accepted work if I change a dependency while the request is running?* This is where Source identity, actor ownership, Datom history, durable evidence, and deployment qualification become one feature a user can experience. A protected edit with missing evidence should leave the previous accepted revision serving. An optional acceleration with missing evidence can use the ordinary implementation if that revision already satisfies its required laws. Those two outcomes deserve different behavior and different explanations in the editor.

* The experiment I would put first

I would take *one tiled integer image operation from the scene renderer*, with a sequential reference and a visible result. The renderer already has deterministic frame selection, captured shaders, worker reports, and revision-aware publication. Today BL owns geometry, composition, and time while workers perform substantial graphics work. That gives us a real application, a current implementation to compare against, and a natural place to see whether editing Enchant source is enough. An integer operation makes the first equivalence claim exact. [[file:../../../examples/scene-renderer/README.md][Renderer architecture and GPU provenance]]

1. *Write the operation once in ordinary Enchant.* Start with packed input, immutable reads, a fresh output, and disjoint tiles. Let the author express the subdivision if inference cannot recover it. Bend persuaded me that hiding every placement or partitioning decision is a poor goal. A programmer often knows which branches should be comparable in cost. The compiler should check the safety facts it can establish and expose the remaining performance assumption.
2. *Give it one law worth reading.* For every admitted image and legal partition, stitching the tiles produces exactly the sequential image, including edge tiles and empty dimensions. Specify channel width, rounding, clipping, and failure behavior. Deliberately change one boundary comparison. The workflow should show the failed obligation or a replayable counterexample in terms of a pixel the author recognizes.
3. *Run the same source through generated BEAM, native CPU, and one real GPU path.* Reuse the current lowerer and runtime machinery where they fit. Record which backend actually executed. Compare an ordinary parallel CPU implementation, the current graphics worker, and equivalent Bend on the same hardware. Measure small edits, a single frame, and sustained batches. Include compilation, packing, queue delay, transfers, result materialization, and unrelated-client latency. A discrete GPU and an integrated GPU can give different answers for sound architectural reasons.
4. *Make an edit while the old frame is in flight.* Change a helper the law depends on. Observe which artifact finishes the old request, whether a stale result can be published as current, and when old buffers and code are released. Then break the law and inspect what stays visible. This is the part of the experiment that could make someone choose Enchant even on hardware where Bend draws the frame faster.
5. *Try a second independently authored operation before declaring success.* If it needs a new handwritten shader, a second semantic descriptor, or a custom proof pipeline, we learned that the first integration was bespoke. If it works and an irregular workload correctly stays on the CPU, we have evidence of a reusable language feature. The existing October evaluation protocol already supplies much of the comparison methodology. [[file:../../scene-renderer-and-bend/bend-comparison/EVALUATION.md][Enchant comparison protocol]]

My strategic bet would be *explicit ownership and parallel structure inside a small compute fragment, with Enchant’s existing live semantics around it*. Global affinity would impose a real cost on persistent data, interactive redefinition, rich effects, and host interoperability. Requiring the compiler to infer everything from unrestricted dynamic code imposes the opposite cost on every optimization. A fresh output buffer and a declared partition give the compiler two powerful facts at a place where the author already understands them. Likewise, a human-owned law gives the proof machinery a question whose answer matters to someone.

The question I would use to revisit the backlog is *“What can an application author now do by editing one definition?”* Bend has a persuasive answer for a parallel sum. Enchant has the ingredients for a more ambitious answer for a running application. I would spend the next increment making that answer observable from source edit through proof, execution, and publication.

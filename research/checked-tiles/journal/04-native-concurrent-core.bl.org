* Start with a process that is already waiting

#+begin_lede
Suppose the application is waiting for a cancellation when its author saves a new handler that also accepts previews. Two well-typed messages are queued, a preview followed by a cancellation. Does the running request disappear, render, or finish under the contract it started with? A language for changing live applications owes the author an answer. Its native compiler must preserve that answer even when it changes how continuations, mailboxes and code are represented.
#+end_lede

I would build Enchant around an explicit meaning for a step of a running program. The self-hosted compiler is the most demanding application of that meaning. It runs ordinary Enchant, performs effects while expanding code, produces new programs, and can itself change between two compilations. The renderer adds a second demanding client: it has a caller, an actor, an asynchronous device and a user-visible publication. If the same account of values, effects, ownership and revisions works for both, we gain a language architecture. If either needs secret rules in its host, we have located an unfinished part of the Core. * Where native self-hosting changes the plan

The native route already goes from original BL through its reader, macro expansion and actual ANF into a BL-owned Scheme emitter, Gambit-generated C and native executables. A qualified BEAM SDK seeds the bootstrap. Stages two and three emitted byte-identical Scheme; three actual executables passed the original source and actor corpora. There were 461 actor checks at each of three turn budgets. A separate native AOT experiment kept old closures alive through replacement and GC. These are different qualifications. The bootstrap can faithfully reproduce a compiler that contains a semantic error. CakeML shows what the stronger claim costs: a semantics, preservation proofs through intermediate languages, and a bootstrap evaluated in the logic that establishes a theorem about generated machine code. [[file:../../native-seed/evidence/scheme-fixpoint/qualification.json][Bootstrap receipt]] · [[file:../../native-seed/evidence/incremental-aot/qualification.json][Native closure lifetime]] · [[https://cakeml.org/][CakeML's verified implementation]] · [[https://doi.org/10.1017/S0956796818000229][Verified CakeML backend]]

I would therefore make the *warm native development host* a first consumer of every new semantic rule. That gives a rule two opportunities to pay for itself. It can make an application faster, and it can make the compiler that processes the next edit faster. Enchant already has more instructive measurements here than an arithmetic microbenchmark. A prepared native image reached the first result and exited in 165 ms median against 4.66 s for the pinned BEAM command on the same small program with warm filesystem caches. In a source-edit experiment, the native updater's shadow path reused 31 of 34 definition sets and matched a clean reference. A deliberately environment-reading macro then changed the generated definitions while observed file and link reads stayed identical. Caching “same source” would have made the compiler faster and wrong. Record macro code, positive and negative lookups, staged reads, fresh-name scope and permitted effects. Refuse unaccounted reuse; keep the ordinary path. [[file:../../native-seed/speed/native-speed.bl.org][Native speedwork and macro controls]] · [[file:../../native-seed/speed/attrib/raw/wrapper-emission-cold-beam-pair.json][Cold command boundaries]]

The native bootstrap has a trusted floor. Gambit supplies representation, allocation, collection and continuations. C, the toolchain, OS and device contribute behavior. The BL emitter currently has a deliberately supported subset. Favor the existing unit store and native artifact owner. Independently record source closure, selected compiler image, emitted bytes, runtime ABI and the executing generation. A compiler edit must be checked by an already accepted tool/semantics generation; a newly edited checker cannot promote itself. Rebuilding from an independent seed, a reproducible emitted fixed point, and a preservation theorem answer different questions. Keep each attached to the exact claim it can support. * What “fully represent” can reasonably promise

**Coverage.** Every admitted source operation should have a path through expansion and resolved ANF to a rule with observable behavior. Classify each actual primitive instance as specified internally, specified by an environment contract, or outside this verified profile. Count dynamic invocation and each admitted FFI capability as obligations. A catch-all host call with an arbitrary result does not justify a theorem about what that host does. It can still delimit a sound conditional theorem. Make uncovered operations discoverable with a source location and caller. Macros belong in this inventory at expansion time as well as their expansions at run time.

**Typing.** A total classifier can always return a type approximation, a diagnostic, or an explicit unknown. The existing tag lattice has a top value; this makes useful inference possible in a dynamic language. A sound classification of a closure as callable says little about the values, errors, effects or termination of an invocation. A typed operational semantics should make it possible to establish preservation and a progress statement that includes legitimate waits, external requests and named errors under a specified environment. A stronger termination claim needs a ranking argument or a restricted total fragment. General Enchant computation includes recursion. A sound decision procedure for termination of all such programs is unattainable. [[file:../../../docs/typing/beam-lisp-type-system.typ][Existing inference policy]] · [[file:../../formal-logic/LOOPS.md][Loop obligations and rankings]]

**Logical totality.** SMT sorts describe domains and function symbols denote total functions on them. SMT-LIB integer division only fixes its quotient/remainder laws for nonzero divisors. Therefore a solver can assign a value to division by zero consistently. BL may raise a named error there. The right question includes success, value, error and evaluation order. Finite machine floats, source exact integers, width-bounded lanes, and host exceptions require distinct interpretations. Existing Enchant work already caught a floating-point cancellation claim that was true over mathematical reals and false in compiled execution. Total terms make an excellent modeling language once this translation is explicit. [[https://smt-lib.org/theories-Ints.shtml][SMT-LIB integer theory]] · [[https://microsoft.github.io/z3guide/docs/theories/Arithmetic/][Z3 arithmetic]] · [[file:../../formal-logic/CORE.md][Returned and raised outcomes]] · [[file:../../formal-logic/FLOAT-SOURCE.md][False numeric agreement]]

**Solver coverage.** A typed encoding for each question must state its direction of approximation. An overapproximation of all reachable states can establish absence of a bad state if the translation is sound and the negation is independently discharged; a satisfying assignment may be spurious. A trace actually replayed from a reachable initial state establishes possibility. Underapproximation or exploration to depth k cannot rule out a deeper violation. Keep higher-order behavior in the operational model: represent a closure by code identity, environment and calling convention, and specialize a call in logic only after resolving or guarding those facts. Treat opaque host behavior through explicitly quantified assumptions. A claim about *every* program in a profile requires a theorem covering its grammar, primitives and translation. Thousands of passing generated questions are useful tests with a different quantifier.

**Execution.** Define how to take a step. A full execution may return, raise, wait for an input, diverge through infinitely many internal steps, or keep producing externally visible events indefinitely. A bounded evaluator running out of fuel establishes the end of its exploration. A finite observation of a silent process cannot decide whether it will ever wake. Interaction Trees are a useful precedent for explicitly representing returns, internal steps and effects in possibly infinite computations; the concurrent Core Erlang formalization shows how to layer local reductions, signals and communicating processes. I would reuse the existing Lean models and transfer these design principles. [[https://arxiv.org/abs/1906.00046][Interaction Trees]] · [[https://doi.org/10.14232/actacyb.298977][Concurrent Core Erlang formalization]]

* A concurrency theory that makes a live edit meaningful

Use a labelled transition relation. A configuration contains the selected code world, actors with continuations and revision handles, mailboxes, in-transit signals, names/monitors/links, outstanding effects, timers, owners of resources and observations already committed. Represent a caller-visible event as data. Representative labels are send, deliver, choose a receive clause, reply, signal process death, publish revision, fulfill an effect and release a borrow. Local arithmetic and many scheduler turns can be internal steps. Capture clock advancement and external input as environment choices. A deterministic replay chooses one enabled transition at each point. The language specification permits every transition that its ordering rules allow.

#+begin_sequence :title "Where the native and logical worlds meet"
lanes app · application | owner · runtime owner | host · native host | check · semantic checker
app -> owner : enter receive under revision A; keep continuation, matcher and capability
owner -> host : park until an input or deadline is ready
app -> owner : accept revision B for new invocations
host --> owner : signal readiness with the operation identity
owner -> check : recorded queue order, selected clause, revision, residual queue
owner --> app : resume the pinned request and deliver its reply
note owner, check : The checker can replay a finite observation. Separate progress obligations explain whether a waiting request eventually resumes.
#+end_sequence

Several practical distinctions follow from that model.

- *Send, delivery and consumption are distinct.* Same-sender signals to the same destination have an ordering guarantee under OTP. Different senders race. Selective receive can skip earlier messages. OTP priority reception changes queue insertion rules; the first Enchant profile here uses ordinary messages. Record whether an implementation promises OTP compatibility or a smaller portable contract. A global FIFO queue would silently strengthen the model. [[https://www.erlang.org/doc/system/ref_man_processes.html][OTP signal and mailbox semantics]]
- *Blocking is local.* A parked actor retains a continuation and relevant code/resources; another actor may progress. The native fixture uses a BL-owned scheduler, an OS worker and an eventfd readiness notification. A host that picks an arbitrary mailbox clause changes application semantics. A host that allocates a continuation differently may preserve every agreed observation. [[file:../../native-seed/real/README.md][Actual timer, FFI and readiness path]] · [[file:../../js-actors-future/03-boundaries-ets-ports-distribution.md][Host/actor boundary]]
- *Safety and liveness need different evidence.* “The old request never publishes as the current frame” is a safety invariant. “Every accepted request eventually gets a reply or an explicit terminal failure” requires assumptions about scheduler fairness, continued service, delivery, worker completion and cancellation. Show a legal starving schedule without the assumption. Give a measure or a fairness argument with it. Weak fairness helps a continuously enabled action; repeated short opportunities can demand a stronger assumption or a redesigned queue. Time bounds additionally need quantitative guarantees. Lamport's treatment of actions, stuttering and fairness is the right discipline. Enchant's temporal interval queries solve a different problem. [[https://lamport.azurewebsites.net/pubs/lamport-actions.pdf][The Temporal Logic of Actions]] · [[file:../../formal-logic/PROTOCOLS.md][Existing finite-prefix induction]] · [[file:../../formal-logic/TEMPORAL.md][Existing interval theory]]
- *Composition needs ownership and a protocol.* Specify what a component may assume about incoming messages and what it guarantees about outputs, lifetime and failure. Show that each peer discharges the other's assumptions. A private reply reference or a single-owner completion restricts which interleavings matter. Session types offer a precedent for explicit conversations among roles. Open mailboxes, supervision restarts, version changes and uncooperative foreign components need explicit boundary contracts. [[https://spiral.imperial.ac.uk/entities/publication/c8344d76-8721-46da-8248-cff7a67de886][Multiparty asynchronous session types]] · [[file:../../execution-protocol-audit/actor-pins.bl.org][Existing graph ownership]]
- *Updates are transitions of the application.* New work may select B while an admitted A invocation finishes. Migrating a parked receive changes control, queue interpretation, timeout accounting, captured state and sometimes outstanding external effects. Preserve or explicitly transform each one. A compatible message schema only proves the new code can read the message. A compatible state schema only proves it can read the state. Either can still change which customer gets answered. Existing migration predicates and Source-owner grants give us components of a stronger safe-point rule. * A small result with architectural consequences

The fresh experiment uses two concrete receive expressions. A accepts =cancel=. B accepts =preview= or =cancel=. The solver chooses two ordinary mailbox slots over three tags. We asked whether both revisions could successfully select a message and choose different positions. Each engine returned the same witness. We enqueued the tags on BEAM, independently ran the two receive clauses, and drained the remaining queue. A consumed =cancel= and left =[preview]=. B consumed =preview= and left =[cancel]=. Both messages type-check; both processes can take a step.

We separately asked whether agreement on the membership of both slots could still yield different positions. Both engines reported UNSAT in that bounded projection. A separate SAT feasibility query exercised a queue with actual progress and matching decisions. Lean checked the corresponding *unbounded-length* statement for the pure first-match model. If the predicates agree on every item currently in a finite queue, scanning yields the same selected item *and the same residual queue*. To promise identical selection on every possible queue, agreement on every individual message is also necessary: a one-item queue distinguishes any differing predicate. A real receive additionally has ordered clauses, bindings, guards, handler effects, deadline races and arrivals after this snapshot. Equal membership suffices only for the projected scan. In particular an empty mailbox trivially satisfies current-queue agreement; a subsequently arriving preview still distinguishes A and B. [[file:../concurrency/Receive.lean][Lemma and converse]] · [[file:../concurrency/receive-check.bl][Actual paired questions and BEAM replay]] · [[file:../evidence/core-concurrency.json][Receipts]]

This suggests a specific native optimization. A suspended receive may retain a compact matcher and continuation descriptor when those capture its full dependencies and the owner keeps their resources alive. It can migrate at a declared safe point if a simulation covers every later input allowed by its protocol, residual mailbox, state and observable effects. Otherwise finish A, or explicitly cancel/drain by the application's rule. Merely re-resolving the handler name on wakeup chooses a different policy. OTP itself distinguishes local old-code execution and fully qualified calls into current code. Enchant should make its own policy visible to the author. * What “correct compilation” should mean here

For a closed, deterministic scalar region, require equality of value or permitted named error and evaluation order where it is observable. For a concurrent component, relate the source configuration to the target configuration: logical actors to physical processes, closures to native code plus environments, logical mailboxes to the queue/cursor representation, and revision borrows to live resources. Under a related environment, every target observation sequence should be allowed by the source contract. Internal target steps may stutter; their infinite repetition must not manufacture starvation or hide divergence when progress is promised. Use a stronger two-way equivalence only when a feature requires preserving alternatives, for example a systematic scheduler exploring all legal orders. Fresh PIDs may be renamed consistently. Observed monitor reasons, message order where promised, user-visible effects and revision IDs cannot be renamed away. CompCert's formulation in terms of allowed observations is instructive. Enchant has different error rules and concurrency, so it needs its own relation. [[https://compcert.org/man/manual001.html][CompCert semantic preservation]] · [[file:../../formal-logic/metatheory/ActorTrace.lean][Current handler-level trace semantics]]

There are two different proof judgments at a live edit. Within revision A or B, compilation must preserve the allowed observations of that revision. Across the edit the author may intend a different answer. Specify a relation between old and new states, pending obligations to callers, already committed effects and future events admitted at the transition. For a compositor that relation may preserve all already promised frames while changing the formula for future frames. For the compiler it may preserve compilation of already captured units while deliberately changing expansion for the next capture. Requiring A and B to be equivalent would forbid the feature being edited; checking each revision in isolation leaves the handoff unexamined. The owner needs evidence for both judgments and authority to perform the handoff once.

A faster compiler and runtime follow from the same distinctions. A pure, bounded computation between effect boundaries can fuse and use narrower native lanes. A scheduler can commute two actions once it establishes independence of mailboxes, code generations, names, timers and resources. Use that independence first to prune test schedules, where a wrong independence claim can be challenged by replaying both orders. Only then consider it for parallel execution. Fairness/deadlines can still make apparently invisible yields observable. Concuerror's systematic exploration gives us a practical model for the test side. Native compilation also needs representation work the solver cannot do for free: root liveness across GC, closure calling conventions, safe suspend points, blocked FFI and the code-reclamation fence. A nicely vectorized helper that monopolizes a service scheduler is an end-to-end regression. [[https://concuerror.com/][Concuerror and dynamic partial-order reduction]] · [[file:../../rt-selfhost/invm/RESULTS.md][Enchant scheduler heartbeat experiments]] · [[file:../Alpha.lean][Range information a native backend can use]]

The comparison to Bend now has sharper axes. Bend 2 gives parallel work a source-level decomposition and gives authors a calculus and checker for laws. Keep that as the comparator for pure parallel work and proof authoring. CakeML is the sharper comparator for a self-hosted verified compiler, and concurrent Core Erlang and OTP for observable actor behavior. On identical hardware and inputs measure cold compiler invocation, warm changed-definition compilation, whole native self-emission, scalar/parallel execution, and time to an accepted live revision during other actors' work. Match numeric semantics, placement, and duties imposed on the checker. An unsupported lifecycle is a difference in contract coverage. It supplies no timing result. * Order of work and a stopping rule

1. *Inventory the executable core using two roots.* Walk the original self-compiler closure and a real renderer's actor entry. For each reachable ANF operation and resolved primitive record phase, normal and error behavior, effects, revision dependency, supported targets, checker connection, and an executable counterexample/control. Track dynamic/reflective imports separately from the finite observed graph. Publish gaps instead of assigning whole-language coverage from a count of opcodes. Include a macro that observes mutable state, an escaped closure, an unmatched receive and a failed foreign call.
2. *Give one native process the whole story.* Park it under A, queue the two tags, edit under B, let a third actor make progress, and wake it through the real input owner. Observe consumed/remaining messages, continuation and generation, response, deadline, single completion and cleanup. Replay on the supported BEAM path. The intentionally wrong “use latest on wake” implementation must fail. A timed-out or superseded candidate must leave ordinary service intact. This joins the proofs and physical runs of this chapter in a single application.
3. *Make the compiler itself the second live application.* While compilation of a captured A is in flight, change a macro helper or lowerer to B. Keep A's result attributable to A; prevent it being installed as B. Show the independent clean build agrees with the warm native result including observed lookup misses, generated names and errors. Repeat the self-emission fixed point at the release boundary. Keep critical compiler/checker state immutable until the preceding accepted toolchain qualifies its successor. Profile cold, warm, retained memory, service tails and throughput separately.
4. *Grow the theorem along actual use.* Extend first-match to ordered clause bodies, guards and timeout registration, then to a pair of communicating actors, monitors and fenced retirement. Add blocking foreign completion, cancellation, crash/restart and durable migration one observable boundary at a time. Test an adversarial schedule and an uninhabited premise at each gate. The long-term success criterion is that every admitted primitive has an explicit meaning and every claimed optimization has a traceable justification. New programs will still pose questions the tools cannot decide.

For the first milestone I would stop expanding the architecture once two facts are true: an author can explain precisely what happens to the already waiting actor, and the native host, BEAM observation, independently checked rule, and running owner's receipt all tell that same story. That milestone pays for itself even before whole-core coverage.

* Which prototypes would clarify the architecture?

My first prototype would drain a mailbox. A receive that matches the head does very little semantic work. In the native host implementation inspected here, removing that head still walks every queued entry. That is the kind of discrepancy we should look for throughout Enchant: which work does the language actually require, and which work did our representation accidentally introduce?

CakeML offers a particularly good design habit. Its space-cost work puts the analysis at DataLang, after closure conversion, where allocation decisions are concrete enough to count. Its compiler paper describes accepting and checking an oracle colouring during expensive in-logic compilation, while the bootstrapped compiler uses its verified allocator. Both choices identify a small interface at the point where a claim is easiest to defend. For Enchant, count mailbox entries at removal, compiler dependencies at invalidation, proof nodes at admission, and resident bytes where a frame changes owners. A single source-level “cost” would conflate all four. [[https://cakeml.org/oopsla20.pdf][CakeML space-cost semantics]] · [[https://cakeml.org/jfp19.pdf][CakeML verified backend]]

** First run: what does a head match cost?

Start with an already populated ordinary FIFO mailbox of N distinct messages. Every receive matches the head, there are no concurrent sends, and the timed interval ends after the last removal. The BL runtime already passes a cursor forward when the same parked receive wakes up. The removable cost here is in =h-vec-remove=: its rebuild loop alone visits N entries, then N−1, down to one. Count visits to that loop as a lower bound on work; conversion to a list, reconstructing the native vector and GC add costs. A queue of immutable chunks with an index into the first chunk could advance a head in amortized constant time, dropping a consumed chunk when its last live reference goes away. Start with the head case. Use the general removal path for an interior match. [[file:../../../priv/lib/js/actor/runtime.bl][Receive and removal path]] · [[file:../../native-seed/host/host-values.scm][Native vector removal]]

This executable cell counts the rebuild visits on small lists, checks them against the recurrence, and compares the delivered order with a head-advance model. The 4,096-entry row is an extrapolation of that exact recurrence. It counts abstract operations with different unit costs. The native actor and a candidate chunk implementation still need instrumentation.

#+begin_src beam-lisp :id mailbox-drain-work
(let [rebuild (fn [items]
                (loop [xs items survivors [] visits 0]
                  (if (empty? xs) [survivors visits]
                    (recur (rest xs) (if (= visits 0) survivors (conj survivors (first xs))) (inc visits)))))
      baseline (fn [items]
                 (loop [xs items delivered [] visits 0]
                   (if (empty? xs) [delivered visits]
                     (let [[next-queue cost] (rebuild xs)]
                       (recur next-queue (conj delivered (first xs)) (+ visits cost))))))
      advance (fn [items]
                (loop [xs items delivered [] moves 0]
                  (if (empty? xs) [delivered moves]
                    (recur (rest xs) (conj delivered (first xs)) (inc moves)))))

** What did changing the data structure buy?

The candidate uses two immutable skew-binary random-access lists. New messages enter the rear. When the front is empty, the first head removal reverses the rear into a new front. Within one queue history each item makes that trip at most once between interior rebuilds. Skew-tree prepend and head removal each touch a bounded number of nodes, and an indexed lookup takes O(log N) worst case. A FIFO drain therefore needs O(N) removal work in this fixture. ** What to change in the compiler next

In the browser run, Lean used 94% of the server's save interval. A native compiler can correctly rebuild one of three functions and still leave the developer waiting nearly a minute.

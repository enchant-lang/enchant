#+title: The same compiler on Chez, and what a user waits for
#+subtitle: A substrate swap reaches warm-BEAM parity on the matched job; the user's wait is mostly outside the compiler.
#+date: 2026-11-20
#+status: Chez image qualified on every Gambit gate · warm floor traced to lock polling · fix pending

* Why this experiment

The handoff left the native compiler 4.8–8.9× slower than warm BEAM. Its diagnosis pointed at the value model the host gives BL, not at a lack of machine code. That left open how much of the gap belongs to Gambit itself: generated C compiled at =-O0=, a large C toolchain in the loop, and a hand-built turn budget. The cheapest way to separate the two was to run the *same* qualified compiler Scheme on Chez Scheme 10.4.1 and change nothing else. [[file:05-native-compiler-handoff.bl.org][Handoff]] · [[file:04-native-concurrent-core.bl.org::Why the native compiler is slower][Earlier diagnosis]]

* What changed between the two runs

=research/substrate-ab/translate.ss= reads =cutover-core-build-v3/prelude.scm= (6.1 MB, 11,101 forms) and writes Chez forms. It rewrites four =#!optional= / =#!rest= lambda lists, five =##= global-variable primitives, the one embedded PCRE2 C block and its six =c-lambda= procedures. It also renames five Gambit procedures whose Chez namesakes take different arguments: =error=, =with-output-to-string=, =getenv=, =call-with-output-file= and =eval=. =chez-shim.ss= supplies Gambit tables, =with-exception-catcher=, error objects and a few string and vector moves. The macro bundle evaluated at run time passes through the same rewrite. No BL source, emitter or compiler algorithm changed. [[file:../../substrate-ab/translate.ss][Translator]] · [[file:../../substrate-ab/chez-shim.ss][Shim]]

* The matched job on three engines

The job is the journal's reader translation: 86,200 bytes, 104 definitions, read, compile and emit inside an already running process. Each arm ran 8 warm rounds in two counterbalanced blocks on Work. The BEAM arm is the pinned SDK running =beam-attrib.bl= with the image's pinned emitter sources, as in =boot/pipeline.py=. All six runs emitted the same 247,738 characters (SHA-256 =9b92b9f2…=). * What it costs to produce and start the image

Chez needs about one sixteenth of Gambit's build CPU and no C compiler. That matters more than the runtime figure. Native code for an edited definition can be produced inside the running process, so the native target and live reload no longer wait on clang. The earlier journal found that raising Gambit's C optimization made the host unit slower or impossible to build. Chez's optimization is a compiler parameter.

The client is one socket request with negligible CPU. A request that compiles nothing still spends 50–170 ms inside the server VM, and that spread is wide because Work is in swap. For a small project the compiler is not what the user waits for. The fixed request path and VM startup are. A 200× gain on unchanged requests has to remove that floor. Caching compiler output alone cannot reach it.

* What this changes in the plan

- Use Chez as the native substrate. The decision is now backed by measurements instead of preference. Keep the Gambit image as the qualified control until the Chez image passes the same gates.
- Qualify the Chez image next: the 461-check actor corpus at the three budgets, the source corpus, and a self-emission fixpoint where the Chez-hosted compiler builds itself. Map the turn budget onto Chez engines only after the existing scheduler passes unchanged.
- Measure the warm request floor inside the VM before building a new cache. If the floor is transport, realm admission or loading rather than compilation, removing it serves every engine and every user immediately.
- The typed private IR, compact nodes and fused macro-result walk remain the route past parity. They now start from 169 ms on this job, not 834.

* Where a warm request waits

A 1 ms stack sampler in the realm VM found a running process in 58 of 520 ticks across 15 warm =bl run= requests. The VM is idle for most of a request. Timed call/return tracing then attributed the wall time. Over 10 requests the user command itself took 251 ms, and =compile:forms= plus =code:load_binary= took 33 ms. Contended node-local lock acquisitions waited in =wait_for_local_lock_retry= 1,910 times, for 4.3 s across processes. The contended key is =bl_native_publication_lock= for the already-loaded SDK modules =BeamLisp.Execution=, =Refs=, =Vm.Session=, =Vm.Net= and =Vm.Io=. About 84 acquisitions per request hold it, through =run_code_callback_entry!=, =retain_code_components!=, =register_code_callback!=, =close_execution_registration!= and =release_eval_module!=. Each retry sleeps on a fresh 1 ms timer whether or not the holder has already released. The full-table ETS scans that =tprof= first ranked highest cost 0.1–0.7 ms each untraced, about 5–7 ms per request. The probes are in [[file:../../substrate-ab/floor/][substrate-ab/floor]].

Two smaller findings. The checkout client recomputes runtime identity with =find= and =sha256sum= on every command, about 0.4 s of CPU. The installed client does not. And the warm VM reports “exit 1 and no output” for errors that a cold run prints in full, including a plain =badarg= or an unbound var.

The next change is a release notification for =with_local_lock= waiters. It keeps the exact-ticket dead-owner recovery and the timer as a backstop, and uses a process alias so a late notification cannot leak into a caller's mailbox. The custody operations per request are the larger structural cost behind it.

* The lock wakeup measured
Commit =60aede9b3= wakes a local-lock waiter when the holder releases the lock or exits, instead of letting it poll on a 1 ms timer. On the checkout SDK rebuilt with that change, the same tracer covered ten warm =now.bl= requests: 467 release-waits held 194 ms in total, and no =wait_for_local_lock_retry= sleep ran. Before the change, the ten requests made 1,910 retry sleeps holding 4,286 ms. [[file:../../substrate-ab/floor/wall-after-lock-wakeup.txt][Trace]]

The checkout request now takes 400–470 ms of wall time, and the client uses 0.34 s of user CPU of it. The Rust client SHA-256s the 976 runtime source files (67 MB under =priv= and =native=) on every command, because =engine_inputs.rs= keeps no evidence between commands. The VM's share of a checkout request is therefore about 20–50 ms. The installed =bl= does not hash anything and was measured earlier at 100–170 ms on the old SDK. The lock change reaches it at the next release. The lease and custody tests pass on the changed SDK: =code_lease=, =code_lease_observation=, =eval_module_release=, =exact_member_lease= and =class_custody_entries=, 112 checks in all.

* A warm command's errors reach its client
A failing command in a warm VM printed only "the warm VM ended this command with exit 1 and no output". The CLI reports failures with =IO.puts(:stderr, …)=, as a cold run does, but =:standard_error= is one registered process per VM, and in a warm VM it writes to the VM's log. The request proxy (=vm.io=) carried only stdout. The session now puts a router in front of =:standard_error=. A write from a process whose group leader is a live request proxy becomes that request's =:stderr= frames, in order with its stdout. Every other write goes to the original device. No call site changed: the CLI, library code and =io:format(standard_error, …)= are all covered, and so are processes the command spawns. A cold VM has no router. =vm.session-test= covers an undefined var, a badarg, an explicit stderr write, stdout/stderr ordering, a spawned writer, and a write from outside any request. All 37 of its checks pass. Through the checkout client, =badarg=, undefined-var and =ex-info= failures now print the same text a cold run prints.

* The checkout client stops rehashing the engine
The Rust client now keeps a content digest per physical path, together with the complete stat stamp it was read under (device, inode, size, mode, mtime and ctime in nanoseconds), in =~/.cache/beam-lisp/checkout-digests-v1.bin=. It reuses a digest only for an identical stamp. A digest is recorded only if the file's newest timestamp was at least 2 s older than the start of its read. A write in the same clock tick is therefore read again, and ctime cannot be set from user space. =BL_CHECKOUT_DIGEST_CACHE=0= turns reuse off. The engine capture on this checkout goes from 0.15 s to 0.01 s with the same fingerprint, and a warm checkout =bl run= from about 410 ms to 60 ms. Edits made 0.1 s apart, a same-length edit, and an edit with its mtime set back to 2020 are each seen on the next command. A new Rust test covers reuse, the racy window and a same-length edit with its mtime restored. Run serially, 113 Rust tests pass. The one failure, =failed_metadata_prevents_real_native_publication_even_with_a_guessed_library=, needs =BL_ARTIFACT_PLATFORM= and also fails at HEAD.

The SDK build for these checks failed at first because the build station's disk was full: 1.8 GB free of 476 GB. =nix-store --gc --max-freed 60G= removed 2,766 dead store paths. No GC roots or project files were touched.

The request path spawns about ten processes per request: five owned starts (each wrapping an inner worker) plus compile workers. The 1 ms sampler found
a running process in 94 of 364 ticks over 20 requests (26%); its top self frame
is =SeqCursor:new/1= (20 samples), from lazy =concat=/=map= in the request path.
A changed user file costs about 1.5-2 ms more in the VM (handler 15.8 vs 13.6
ms); in the client total it is inside the noise.

Three removals, largest first:

1. *Cache the tree's generation outside the request process.* The engine and
   project generations are content-fixed and recomputed on every command: 34
   ms, two thirds of the floor. A per-tree resident (inotify, or the realm's own
   directory records plus the digest cache) answers them from one token:
   50.7 → about 17 ms.
2. *One request, one process.* Run the command in the connection process with a
   realm handle opened once per generation, write to the socket directly, start
   the heartbeat only past a threshold, return on the same connection, and skip
   custody registration for an unchanged module set (U4's target): the 9 spawns,
   =realm/open=, the proxy and heartbeat, and the registration cost are 11 ms of
   the 13.6. VM handler ≈ 2-3 ms.
3. *Compact, keep-alive request.* A persistent connection removes connect+hello
   (1.2 ms). Sending argv, cwd and an environment generation instead of 91
   variables removes a 10 KB frame, its validation and the 58 lazy cursors. A
   user file cached by source hash turns =run_file= + =eval_string= (4.3 ms)
   into a call; changed files still pay their 2 ms compile.

With all three, 1.5-2 ms is reachable: ~1 ms of process exec for a small
launcher, 0.1-0.3 ms for one AF_UNIX round trip, and ~0.5-1 ms of BEAM work with
no spawn and no realm lookup. Going below 1 ms needs the client not to be a new
process per command (a resident client) and a smaller launcher than the shell
script plus =dirname=/=readlink=; the irreducible part is one scheduling hop,
one socket round trip and the print.

* The warm floor, 34 ms removed
The two content-fixed client costs — the engine inventory (22.8 ms, 976 files
verified by stat stamp) and the project generation (~11 ms) — were recomputed on
every command. A per-tree resident now answers them. It is started by the first
client that misses it (`drop-launcher --generation-service ROOT`, detached) and
is optional: `BL_CHECKOUT_GENERATION_SERVICE=0` disables it, and every failure is
a fallback to the same local computation.

The resident is the authority for "did the tree change", backed by the kernel.
It watches the engine tree, the project tree and the extra roots with inotify;
an `L` file's parent and every `D` directory the realm's manifest recorded are
watched too, so a new candidate or an edited loaded file is an event. Every
answer drains the queue immediately before replying; any event invalidates the
affected scope, and the scope is recomputed — never guessed. Watches are
installed before a computation, so an event during it turns the answer into a
fallback. `IN_Q_OVERFLOW`, a failed watch, a replaced root (dev+ino change) and
a non-local filesystem (the `statfs` magic is checked) all yield `fallback`.
The tokens are produced by the same `checkout_generations()` the client uses, so
a cached and a local answer are byte-identical (unit test). The realm stays the
authority for retirement: it holds the token it was opened against and retires
when the client's differs.

Measured with the branch's launcher on the `/tmp/u9root` harness, load average
6.6 on 16 cores, 20 runs: baseline (service off) median 43.1 ms; warm service
median 16.9 ms — 26.2 ms removed. The phase marks show the mechanism: a service
query is 340 µs, the local computation it replaces is 26.2 ms. An edit to a file
the realm recorded retires it (stored generation and env ref change; the next
run prints the new value); an edit to an unrelated file keeps every token; a
new file appearing in a recorded search directory changes the project token.
`cargo test` passes everything it passes on main (the two `builder_tests`
native-publication failures need store custody this sandbox lacks). The gate:
the ten realm/seed/JS files 10/10 forward, reversed and forward again,
`loader_sources_test` 43 and `loader_sources_realm_test` 4, `seed_runtime_abi`
11/11 warm twice, `warm_request_env` 3, and the helper-edit scenario.
Evidence: =research/checked-tiles/evidence/warm-floor-u10.json=.

The first cut of the resident failed in a real checkout, and the reasons are
worth keeping. It watched the WHOLE checkout root recursively, so a real tree
(research/, .git, generated trees) put the first answer seconds past every
client timeout; a manifest `D` line was watched through its PARENT, so a
recorded search root under /tmp made /tmp watched and unrelated temp traffic —
including the resident's own debug log, which it had put in /tmp — invalidated
the project pin on every answer; and there was no single-instance lock, so two
clients could each start a resident. The fixed plan watches the engine policy's
roots recursively, the checkout root and project root non-recursively, the
declared/extra roots and `overrides/` recursively, and manifest entries (a `D`
directory itself, an `L` file's parent), capped at 20,000 watches. Recorded
inputs that no longer exist are not watched through a shared ancestor; they are
stat'd once per answer, so their reappearance invalidates without /tmp noise.
One resident per root is held by an `flock` on `<socket>.lock`, and the winner
unlinks a stale socket instead of serving it. On a scratch copy of main
(engine and project trees only, load 6.9): warm `run` 55.7 ms with the service
off, 18.7 ms with it on (−37 ms); a warm direct probe to the socket answers in
0.27 ms; two simultaneous starts leave exactly one resident; the ten files pass
in three orders on that copy, seed_runtime_abi passes warm twice, and the
helper-edit scenario is green.

What remains for 1 ms is the VM side: the handler is still 13.6 ms, of which
about 10 ms is per-request process spawning, the re-opened realm and custody for
unchanged modules, and the rest is re-evaluating the user file. The next two
removals are the VM's one-request-one-process path and a compact keep-alive
request.

* Where compilation now goes, and what the IR has to change
Compilation is now 102 of the reader job's 149 ms, and no host leaf above 3% remains. The time is in the compiler's own data path. A macro expansion is walked four times:
1. =datum= turns each argument form into data.
2. =check_first_order!= walks the result. For every node it allocates a budget tuple, and for every atom it builds a binary just to take its size.
3. =data->form= turns the result back into reader nodes.
4. =renumber= rebuilds it again for gensym canonicalization, threading a persistent map.

Generic BL maps with keyword keys hold every node, so each field read is an ordered small-map search with keyword comparison.

The private IR therefore has to change the compiler source (=priv/boot/compiler.bl=, =priv/host/compiler_data.bl=), not the host:
- fixed-layout records for reader nodes and ANF, with field access by position;
- one fused validate/convert/canonicalize pass for macro results, charging the same budget in the same order;
- keyword fields resolved at compile time.

The BEAM compiler compiles the same source, so its output has to stay byte-identical. The native image then has to be rebuilt from BL through the BEAM-seeded stage 1 and requalified (stage 2 = stage 3, corpus, actors). That is the next piece of work. Host-level tuning has reached its limit.

* Compiler-source candidates without BEAM
Each of the 34 units in the qualified native bundle carries its BL source, and every one of them is byte-identical to its file in this checkout. =native.bootstrap/prepare= compiles a unit from that text. So a compiler change can be built and qualified on Chez alone:
- =bundle-src.py= extracts or replaces unit sources.
- =compiler-candidate.py= injects the checkout's sources, has the qualified Chez stage 1 compile the new bundle (S2), and runs =chez-fixpoint.py= on S2 as both stage 1 and expected stage 2. The checks are: both corpora; S2 compiles the new bundle into S2 again, meaning the changed compiler emits what the qualified one did; stage two equals stage three; and the actor corpus at all budgets.
- It adds one gate: S2 compiles the original bundle into the qualified image's =stage2.scm=, byte for byte.
A candidate takes about three minutes. =derive-image.py= now diffs every top-level form (it had silently skipped =native-add-leaf!= registrations), replaces exact source spans and anchors insertions.

The first compiler-source change makes =renumber= return whether a subtree changed. It hands an unchanged node back only where a rebuild would give an equal node: 3-element =:meta= wrappers, 2-element composites and 2-tuple map pairs. =gensym-base= rejects any name without the =__auto= suffix before measuring it. That candidate passes 13 of 13 gates. * Why shard children refused their root
OTP answers =code:priv_dir(beam_lisp)= only through a code-path ebin whose parent directory is named =beam_lisp= or =beam_lisp-VSN=. The library root is =beam_lisp-0.1.0= for exactly that reason, but each shard's ebin sat under =shard-shard-i/=, so the child resolved the parent VM's own =beam_lisp= and the producer refused the staged root. Two Erlang VMs with differently named directories reproduce it in a second. Each shard is now a sibling application root with the library root's own name (its own =ebin= beside a =priv= link), and the child compares =Tiers/priv_root= with the staged root right after boot, naming both paths when they differ. The general lesson: the SDK root is inferred from a naming convention in one place and passed explicitly in another, so the check belongs at the start of the child, where both are known.

** Proposal for the largest phase

Phases 4 and 5 with the repeated priv sweeps are the target; nothing smaller is worth doing first.

1. Walk the SDK inventory once per VM. For an image under =/nix/store= or a drop directory, whose bytes are immutable by identity, take the digest and receipts from the sealed manifest and skip re-reading source files; keep the full walk for mutable checkouts. Expected effect: the 1.5–1.7 s of sweeps shrinks to one 80–100 ms read (the first sweep, which reads 666 files), so a cold run drops from about 4.3 s to about 2.9 s at load 4, and from 6.1 s to about 4.5 s at load 10. * U8: the producer seals the seed proofs

Decoding a seed is pure work over sealed bytes: read them, sha256, BEAM MD5, chunks for imports and role, ctor and lambda origins, and for shims a disassembly of the forwarding routes. A cold start did that for the seeds it loads (5.2% of running samples in U7's sampler). The bytes cannot change under an immutable image, so the producer now derives the same rows once in =do-prime= and writes =priv/seed-metadata.term= (105 rows, 716 KB, deterministic).

The reader checks three things and then uses the row: the table and seed directory are both under =/nix/store= (a checkout or writable drop decodes as before); the table names this compiler key and the MD5 of the AOT module that derived the rows; and each row's digest equals the manifest's digest for that seed, which is the same string the decode compares with the file's sha256, plus the proof's own =:sha256=. Every row's proof is its own term, so reading the table (8.3 ms) does not decode proofs for seeds a VM never loads. What the reader stops doing is re-demonstrating that the proof is a function of the bytes; in a sealed image that demonstration is the publisher's, and the executable checks are unmoved: =seed_artifact_proof= still compares the proof's MD5 with the live module, and forwarder rows still pass =Env/sdk_forwarder_current?= against published native routes.

Measured in the checker on the store image (load 10-22): deriving all 105 proofs 231-311 ms; reading the table 8-9 ms; taking all 105 rows 53-73 ms. That is about 2.4 ms to derive a seed against about 0.5 ms to take its row, so a cold start that loads ~95 saves roughly 175 ms of 3.4 s. The end-to-end figure needs a built SDK: run =scripts/coldstart-probe/run= before and after, and the =seed_metadata_table_test= (447 assertions: every sealed row equals the in-VM decode term for term) with the seed/publication/env tests on the built image.

** Built-SDK check: the floor is compiled, the table is read

The first built-SDK gate reported =seed_metadata_table= undefined and a keyword-call error. The undefined half is explained by the floor: a compiler generation's =seed/produce-artifacts= compiles every =priv/host/*.bl= from current source into the produced floor, and =nix/bl-drop= installs that seed, so a new AOT function reaches a built SDK without regenerating the committed =priv/bootstrap/seed= (which still carries the old AOT). The two SDKs built from batch-12 sources, =6vsqnc…= and =wf7s1q…=, have =seed_metadata_table=, =prime_seed_metadata!= and the reader in =image/ebin=, and a 139-row =priv/seed-metadata.term= whose =:decoder= equals the image AOT MD5. On =6vsqnc…= the seed tests pass: =seed_metadata_table_test= 588 (including a new case that asserts a built image reads the sealed table, decoder and Core row), =perf/seed_metadata_cost_test= 2, =seed_publication_test= 227. No manual regeneration is needed; doing it would rotate the compiler key for every cache. The keyword-call error was not reproduced in any configuration tried (new SDK, old SDK with the checker's host overlay, the batch-12 integration tree with the batch-12 SDK, the whole seed suite in one VM); the stack was requested.

Paired cold runs at load 23–27, alternating, four pairs: the previous SDK (zzblkn) 3,902 / 4,242 / 3,280 / 3,203 ms, median 3,541; the U8 SDK (6vsqnc) 2,770 / 2,561 / 2,648 / 2,583 ms, median 2,616, about 26%. That pair spans U6, U7, U8 and batch 11/12, so U8's own share is the seed rows only (about 0.2 s from 2.4 ms to 0.5 ms per seed).

* K1: sealed boot state, and what a seal cannot reach

Card K1 asked for the post-start runtime state as one sealed artifact. Measured first: the current store SDK (=2nvkh1…=) runs a cold =bl run= of =(println 1)= in 2,691–3,079 ms (median 2,777, load 36–43). Cut at =start_app!='s own stage boundaries (=scripts/sealed-boot/phases.exs=): erts and Elixir 260 ms, dependency apps 75, the =:beam_lisp= app start 1,870, =vm.native= =build-all!= 90, loading =bl.cli= 300, the run 55, halt 35. The app start is the target, as U5 said.

A deep-stack sampler (running processes plus those blocked on the file or code server, depth 80) showed what the start re-derives on an immutable image:

- the sealed seed table (U8) was read and sha256-hashed, 0.9 MB, on every seed miss: about 100 times, 7% of samples;
- =packaged_compiler?= walked all of =priv/**= for each source suffix from five call sites (the live compiler and build keys, =Env/live_toolchain_keys= with its own stat stamp of ~250 files), about 6%;
- =bootstrap_sdk_native_hosts!= globbed and stat-ed every tier source, and re-parsed with the reader the ten sources that only mention =defnative= (the compiler, the loader, =aot.bl=), because a stored nil answer read back as a miss;
- the floor proof =sdk_preinit_floor_ready?= ran twice: the proof loads the modules it checks, so the inputs it memoized under (nil md5s) never matched again;
- every image unit the SDK closure touched was read, hashed and decoded (=beam_lib= chunks, forwarder disassembly).

Each of these is a function of bytes under one content-addressed root. The branch derives them once per VM for a =/nix/store= root, or seals them at SDK build time in =do-prime=: =priv/image-metadata.term= (U8 generalized to the 2,567 =sdk-code.term= rows: 6.5 MB, deterministic, 4.9 s to prime; a row is used only when its =:sha256= and the sha256 of the caller's whole row match, and only from an immutable root), =native-declarations/<key>/declaring.term=, and negative native declarations under a separate =.none= name. A writable checkout or drop keeps today's path; loaded code is still MD5-checked at every use and retention.

The first version stored negatives in the old file name. A scratch-image control running the unchanged SDK code then crashed at start on =(elem :none 1)=, because it shares the per-user AOT cache under the same compiler key. Six such entries had been written to =~/.cache/beam_lisp/aot/native-declarations/e86a…/= (the current SDK's key). They were deleted, and negatives now use their own name, which an older reader never opens.

Verified without an SDK build: =scripts/sealed-boot/build-image= copies the store image, overlays the edited host beams that =scripts/check-runtime-hosts= compiled, runs the sealing functions in a second VM and adds the result to =/nix/store=. The overlaid beams are restamped with the shipped source digest, so the compiler key stays the same; that is an experiment device, not an SDK. =scripts/sealed-boot/measure= then alternates paired cold starts through the SDK's own =boot.exs= path. The sealing VM decoded all 2,567 rows live and found them equal to the table. Five rounds at load ~8:

That is −27% against the SDK and −24% against the control. It does not reach the card's 1.2 s. After the change the same sampler puts the remaining app start in three places. Namespace loading (=compile_sdk_source!='s retention, preload and callable checks, then the namespace initializers that publish ~1,400 definitions) is about a third of the samples. The owner registry's =prepare_sdk_class!= walks and leases the whole SDK runtime closure, loading the modules it proves; that is about 15%. The native host stubs are compiled at every start (=compile:*=, 3%), because their bytes embed the image's physical =.so= path. Those are executions, not derivations: what they leave behind holds loaded code, pids, leases and ETS custody rows, so it cannot be written to a file and read back the way a decode can. Getting to 1.2 s needs either a lazy owner registry and SDK lease (the first actor pays, a =bl run= does not), or a restorable Env snapshot that carries no process identity. Both are design changes, and neither is a seal.

* Start with the experience
Team Machine gives work a place: people, knowledge, tasks, reviews and procedures.
Station supplies the operational capabilities: folders, services, tools, messages
and recovery. Namespace imports let each call an explicitly exported capability
while its owning application remains the authority.

These are three connected dossiers, not three alternate product proposals:

- [[/dossiers/team][Team Machine · Gather]] — the workspace, extended through its existing shell and components.
- [[/dossiers/station][Station · Cassette Futurism]] — the same work from the machine's existing deck.
- This inventory owns the complete numbered list and the implementation boundaries.

[[/team?view=today][Open Team Machine]] · [[/station?view=today][Open Station]] · [[/sources/inventory.org][Download this Org source]]

The two mockups share one browser-session rehearsal. Actions change that state,
produce receipts, survive refresh and appear in the other interface. A new browser
context gets a separate world. Reset affects only that rehearsal. All people,
services, counts, jobs, grants and publications in it are illustrative. No action
runs work, changes a real folder, sends a real invitation or writes production data.

* Three implementation states
Connected means the native namespace bridge already implements the capability.
Connect means the underlying feature exists but needs a selected export, host
adapter and product wiring. Build means additional domain behavior is required.
The mockup can demonstrate all three; a working rehearsal is not production
qualification of a proposed export.

The current production source surface is workstation.services/services-in and
inspect. Service projection includes freshness and explicit refresh failure.
The native protocol has separately qualified local and cross-VM invocation,
provider-neutral identity, namespace policy, source admission and lifecycle fencing.

* Capability contracts
Each entry keeps the original number and the behavior requested in the feature audit.

** 01 · Project service discovery
Find services by the authorized physical project root, including saved declarations and observed listeners.

Authority: Station. Production state: connected.

** 02 · Individual service inspection
Inspect one service without exposing another project or private process arguments.

Authority: Station. Production state: connected.

** 03 · Availability and freshness
Show URL, owner, listening and publication separately; preserve previous data on failed refresh and label it stale.

Authority: Station. Production state: connected.

** 04 · Choose a Station project
Bind a place to a stable project identity and its authorized physical folder.

Authority: Station. Production state: connect.

** 05 · Compare place and folder access
Show app membership and Unix folder grants separately; neither implies the other.

Authority: Both. Production state: connect.

** 06 · Share and join a folder
Owner grants or revokes read/read-write; the recipient joins without replacing an occupied path.

Authority: Station. Production state: connect.

** 07 · Project toolbox
Open declared shell, REPL and desktop tools; executable and working directory come from host profiles.

Authority: Station. Production state: connect.

** 08 · Project previews
Start a bounded project preview and show its actual readiness and endpoint.

Authority: Station. Production state: connect.

** 09 · Service lifecycle
Start, stop, restart, boot-enable, withdraw publication or remove the saved declaration with separate grants.

Authority: Station. Production state: connect.

** 10 · Updates and rollback
Select an admitted immutable release; keep the previous version and report activation outcome.

Authority: Station. Production state: connect.

** 11 · Bounded service logs
Read authorized, bounded and redacted log excerpts beside the failed work.

Authority: Station. Production state: connect.

** 12 · Project runtime health
Project-scoped process, memory, swap, failed-unit and history observations.

Authority: Station. Production state: connect.

** 13 · Running runtime versus pin
Show the observed executable and build separately from env.bl declarations.

Authority: Station. Production state: connect.

** 14 · Document VM pools

Authority: Station. Production state: connect.

** 15 · Station handoffs in Today

** 16 · Handoff to task or review

Authority: Both. Production state: connect.

** 17 · Topics and place routes

** 18 · Claims and assignments

** 19 · Portable entity snapshots

* What each system owns
#+begin_rosetta
Fact or action | Authority | Other side receives
Places, tasks, plans and shared knowledge | Team Machine | Authorized projections and typed command receipts
Service lifecycle, process observations and publication | Station controller and existing host owners | Bounded project observations and operation outcomes
Original folder grants | Station sharing service | Current access, join result and explicit owner decisions
Threads, audience and recipient triage | Station messages | Authorized conversations and fixed attachment snapshots
Procedure runs and review decisions | Team Machine / Ensemble | Pinned definition, intent, source basis and result receipt
Client credentials and private contributions | Client portal | Deliberately exported events and selected revisions
Product invitations and release truth | Product provider | Authoritative operation receipts
Root deployment and OS accounts | Existing operator path | Review requests and reported outcomes
#+end_rosetta

* One handoff, two interfaces
#+begin_sequence :title "From an incoming message to reviewed work"
lanes ahmed · sends the handoff | station · owns the conversation | machine · owns the task | othman · reviews
ahmed -> station : Send a brief snapshot to the intended audience
station --> machine : Authorized received work, source reference and basis
othman -> station : Claim the incoming work
othman -> machine : Create one linked task
machine --> othman : Stable task receipt; repeated conversion returns the same work
othman -> machine : Review the current source and complete the task
othman -> station : Reply with the result, then mark received work handled
station --> othman : A later incoming reply reopens received work
#+end_sequence

Claim and assignment coordinate responsibility. Reading, handling and task
completion remain distinct. A sent snapshot never changes when its source does.
Opening a current source checks current access; a message grants no live-world access.

* The interface rule
Namespace declarations own exports, application grants, roles, resource selection
and effect budgets. env.bl owns placement and bindings. Screens, procedures and
agents call the same guarded operation. The host owns trusted resource adapters.
A person cannot provide a replacement identity, role list, executable or credential.

Writes need expected source revisions, stable request identities and durable
owner receipts. A timed-out or interrupted write is uncertain until inspected.
The namespace transport does not automatically replay it. Local placement is not
an exemption from the same authorization or finite-data boundary.

* Walk the complete rehearsal
1. In Team Machine, claim Ahmed's handoff, create its task, and open that task in Station.
2. Start the review preview in Station. Open Team Machine's services and see it listening.
3. Disconnect the fixture provider. Refresh fails visibly while previous rows remain available as stale observations.
4. Reconnect. Switch to Ahmed's reader role; operational writes are disabled and forged submissions are refused.
5. Edit the brief. The live source advances while the received snapshot stays at revision 7. Accept and share the new revision.
6. Prepare a brief job, inspect its commit receipt, return or keep the output.
7. In Client handoffs, rehearse a lost product reply and inspect the existing receipt. The invitation execution count stays one.
8. Move document placement, request a separate restore copy, and queue an operator review without performing a root action.
9. Open Company system to exercise explicitly labelled future-feature models; they do not change implementation status.

* Delivery order
First connect project selection and access observations, Station handoffs in
Today, portable snapshots, and bounded service logs/status. Next connect durable
procedure jobs, client/product operation surfaces and recovery observations.
Recurring business work, outbound reporting, broader funnel behavior and browser
pairing remain domain implementation projects, even though they can share the
same authenticated namespace boundary.

#+title: Enchant performance implementation plan

* 1. Test hypotheses before running qualification

Use the exact pinned SDK and separate preparation, staging, lowering, emission,
linking and startup. Keep small fixtures and one real workload for each change.
Measure an uninstrumented pair in both orders, then trace separately to count
the work responsible for any difference. Record Source, SDK and artifact
digests, wall time, reductions, retained bytes or peak RSS as appropriate, and
the exact output comparison. Record startup separately from warm reuse.

- For emission, vary nesting depth independently of output size. Replace
  repeated copying of the accumulated wrapper with ordered fragments and a
  single join. With wrapper size proportional to depth =d=, accumulated copies
  cost =Θ(d²)=. The join costs =Θ(B)= for =B= output bytes. The depth-256
  control reduced allocation from about 27 MB to 128 KB. The native wrapper
  passed the exact Source and actor qualification.
- For lowering, vary the number of queries independently of distinct provider
  search contexts. The declaration snapshot changes filesystem work from
  =O(QP)= to =O(CP)= for =Q= queries, =C= distinct contexts and up to =P=
  candidate paths. Preserve negative results, resolution priority and the
  boundary where a new declaration snapshot starts.
- Keep the complete qualification matrix for candidate artifacts. Use focused
  probes while comparing alternatives and diagnosing failed preconditions.
  [[file:../../research/native-seed/speed/native-speed.bl.org][Compiler probes, complexity and qualification]]

* 2. Make native edit and retry loops reuse checked work

Keep the current updater as the reference implementation. Bind each lowering
receipt to the qualified donor closure, the SDK descriptor, the installed link
table and the prepared inputs. Use the donor's partitions as the definition
store. Record ordered reads and writes, including missing Source candidates and
missing registry keys. Stage again against the candidate rows. Use a reverse
index from observed links to readers once the current checks can establish all
other inputs. The Lean result covers selection on complete observed inputs.

Current checks reproduced all 34 definitions after a body edit and after an
arity edit that changed the installed rows. Each reused 22 definitions. The
remaining implementation starts at the compiler APIs that own the observed
reads:

1. The bound replay now records namespace readiness, configured search paths,
   loaded BEAM identity, misses on the BEAM code path, selected Source paths
   and declarations. It also checks operation classifications, application
   settings, working and library directories, and code-server availability
   checks. The capture gate refuses operations outside the traced and
   supported calls. Keep units with private Env work on the full-lowering path.
   Keep macro execution, writes, process effects and unknown reads on the
   full-lowering path unless there is an independently checked model.
2. Where a compile scope fixes its roots, pass that root set into the loader.
   For live search roots preserve mid-pass changes. A late-root control
   already demonstrates why an unconditional snapshot changes behavior.
3. The linked updater now accepts a v9 receipt request through
   =NATIVE_CHECKED_RELINK_REQUEST=. The first pass still derives the candidate
   member rows from current Source. The linked pass checks those rows against
   the receipt, stages each member, and writes complete units from the
   qualified donor or fresh lowering. The arity-edit fixture built this
   candidate before running the ordinary updater. It reused 22 units, lowered
   12 and matched both complete ETF files byte-for-byte. The fixture selects
   this comparison with =NATIVE_RELINK_COMPARE=1= and =--capture-local=.
   Keep request and member identity in resume plans. On restart verify the
   plan and input digests before skipping completed jobs. Extend the updater
   comparison to body, provider preference, macro, ancestor, SDK and
   interrupted-build changes. Repeat with altered receipts and mixed artifacts.
4. Measure one-edit and restart workloads including plan and receipt costs.
   Require exact partitions, link rows, emitted bytes and the existing native
   Source, actor-budget and fixpoint gates before selecting the candidate.

* 3. Reduce CPU and retained memory on actual Enchant workloads

Keep the editor benchmark on real LSP open, edit, diagnostic and close
requests. Measure document-owned analysis while moving through many revisions,
then close or replace the document and check that the owner releases results.
Run concurrent revision and reopen controls so a late answer cannot reacquire
old state. Sample whole-realm RSS independently of owner-local retained bytes.
The initial retention fix and its real LSP replay are implemented.

Station's accounting publisher now groups facts by UID in one pass and can
publish through the managed derivation owner on a compatible SDK. Keep report
parity and stale-file availability through refusals, expiry and concurrent reads.
The next implementation records a transaction's changed facts on the committed
basis, applies reversible counters and bounded expiry, and retains the top
request rows with stable tie-breaking. Use the existing full rebuild for an
unknown producer, gap or incompatible basis. Test replacements, completion
of a previously open request, late data, equal timestamps, and events that leave
just one of the windows. Compare every window, UID, gap count and history row
to the current publisher. Replay at 3k, 30k and 74k facts, measuring preparation,
shape, serialization and verification individually. A full report still costs
=Θ(B)= to write for =B= bytes. Attribute remaining cost there before changing
the public report representation.

* 4. Qualify native wins at the user entry point

Keep separate baselines for prepared cold commands, first builds, one-edit
rebuilds and warm resident commands. The prepared cold product already beat
the pinned BEAM control on the small command measured. The next claim needs
the same useful workload, inputs, warmed state and output for each backend.
Use the existing native reader and linked compiler workloads alongside a real
command workflow. Include adapter, dispatch and initialization costs.

Count operand classes and fallback frequency before specializing another hot
operation. Try a narrow candidate with an exact checked general fallback.
Compare against both generic native and the relevant BEAM path. Keep the
candidate conditional until it wins end to end and preserves original Source,
actor, failure and fixpoint behavior. Record cases where a resident BEAM VM
wins and use the result to decide which command should select native.

* 5. Make freshness and wasted work inspectable

Use existing compiler, editor and derivation owners as the source of receipts.
Expose bounded revision, dependency, outcome, elapsed time, work reason and
retention metadata under the existing principal and read grants. Give the
Observatory a receipt link from a visible revision so a developer can follow
admission, wait, compute, reuse, publication or refusal. Use bounded history
and report an expired receipt explicitly. Sampling should leave dormant owners
dormant and should never decode the owner's result payload. Add exact controls
for coalesced work, refused publication, stale retained values, eviction and
principal isolation. Measure the publisher with an absent and a connected
observer. Extend current bounded publication receipts through the remaining
actual tool and dashboard entry points.
[[file:../../research/work-observatory/IMPLEMENTATION.bl.org][Observatory workflows and instruments]]

* 6. Use formal admission to share provably equivalent preparation

Share prepared graph inputs under the exact normalized input, projection and
authority scope. Keep proof and model evidence in the owning runtime. In the
UI distinguish the accepted observation, the evidence that admitted it and
the portion still unknown. The existing graph comparison matched all 748
points while sharing preparation. Apply the same admission contract to the
next repeated query or transformation only after measuring duplicated
preparation. Validate changed inputs, unavailable evidence, budget exhaustion,
concurrent readers and cross-principal rejection. Check effect and ordering
assumptions before reusing a result. Use the original exact interpreter or
qualified release path as the comparison.

For mailbox and concurrent native experiments, separate a proof of compiler
preservation from compatibility with a particular update and from bounded
solver exploration. Replay any solver witness on BEAM before using it to
guide an optimization. Measure realistic mailbox depth and selective-receive
patterns before implementing a different dispatch representation.
